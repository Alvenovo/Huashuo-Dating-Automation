# 交付前验收：手册能不能被照做

> 最后更新：2026-09-21
> 状态：已确认（本轮实跑得出）
> 触发：改完 `tools/` / `hall_auto/` / 《测试机操作手册.md》之后，**发出去给测试同事之前**

## 为什么需要这一份

2026-09-17 → 09-21 期间，同一件事被复核了三轮，**每轮都能查出真缺陷**（3 → 7 → 3 处）。
根因不是代码质量，是**验收方法**：

| 方法 | 结果 |
| --- | --- |
| 读代码、对命令名 / 步骤名 / 参数个数 | ❌ 对得上但跑不通。三轮里第一轮就是只做了这个 |
| 在本机按手册跑一遍 | ❌ 本机是"跑了两年的老机器"，`installer_dir` 躺着 7 个旧包、`config.local.yaml` 是配好的 —— **本机有什么，正好把新机上的坑全盖住** |
| **用临时目录模拟新机初始状态，跑真实代码** | ✅ 三轮里唯一能挖出硬阻断的方法 |

**核心判据：本机跑得过 ≠ 新机跑得过。** 只要验证用的是"本机现状"，就一定漏掉新机上的坑。

## 新机的初始状态长什么样（模拟时必须照这个摆）

| 维度 | 新机 | 本机（会骗人的那个） |
| --- | --- | --- |
| `config.local.yaml` | **不存在** → 读到 `config.yaml` 的占位路径 `C:/Users/ASUS/...` | 存在，且是配好的真实路径 |
| `installer_dir` | **空目录** | 躺着 7 个历史安装包 |
| `_cache/` | 空 | 有 |
| 环境变量 | 空（管理员窗口尤其） | 常驻着 `HALL_FARM_ROOT` 等 |
| 共享盘 | 未认证 | `/persistent:yes` 挂着 |
| 计划任务 `HallAutoP1` | 不存在 | 已建 |

## 怎么做（一次实跑，20 分钟）

写一个**临时审计脚本**（放 `%TEMP%`，不进仓库），用临时目录 + **import 真实代码**，把手册的每条承诺变成一条断言：

1. 列出要验的承诺：12 步顺序、每步的预期输出、失败分支的提示语、落盘字段、套件名单。
2. 用 `tempfile` 造新机：空 `config.yaml`（从仓库拷模板）、空 `installer_dir`、清掉相关环境变量。
3. 对**纯函数**（`step_write_local_config` / `_ensure_seven_zip_fixture` / `take_task` / `cmd_aggregate`）直接调，不整个跑 bootstrap（会真装 7-Zip、真建计划任务）。
4. 需要整条链路的（dispatch → agent → 回执 → 证据 → aggregate）用**本地目录**当农场根跑一次，套件挑 `unit`（不碰界面、1 分钟）。
5. 断言失败时**先怀疑自己的测试**，再怀疑代码 —— 本轮 3 个 FAIL 里有 1 个是我的测试包 sha 不对、1 个是我的正则写错。

**收尾铁律：断言不能留在临时脚本里。** 每条确认的缺陷都要变成一个常驻回归测试（本轮固化了 34 条），否则下一个人还会踩。

## 本轮用这个方法挖出来的 6 个真缺陷（都已是历史，留作模式参考）

| 模式 | 具体表现 | 为什么本机会盖住 |
| --- | --- | --- |
| **回执与汇总的数据没接通** | `aggregate` 报告的「凭据」列恒为 ✗（凭据只写在 `done/` 回执里，汇总只读 `results/`） | 本机从不跑多机汇总，`aggregate` 只被"列在不在"检查过 |
| **取包链少了共享盘那一段** | 离线新机上共享盘明明有钉住包，7-Zip 装不上、`reset_fixture` 报「包不存在」 | 本机 `installer_dir` 直路径就有那个包 |
| **落点与查找位置不一致** | 包取到 `_cache/fixtures/`，而 `update_package_path` 只认 `installer_dir/fixtures/` | 同上 |
| **自检名不副实** | bootstrap 第 12 步 `-m unit` 只跑 127/260 条，漏掉的全是多机链路模块 | 本机从没数过自检到底跑了几条 |
| **文档承诺 ≠ 代码行为** | 手册写 `login-manual`「永不进农场」，`dispatch` 照投（节点会卡在等输入） | 本机从没真投过它 |
| **证据错认** | 本轮没产出证据目录时，回传的是**上一轮的旧目录**（张冠李戴） | 本机每次都跑得出证据，这条分支进不去 |

## 复核《测试机操作手册.md》时逐项要对的清单

- [ ] 12 步**顺序**（顺序错会让环境变量白设 —— 管理员窗口不继承 `$env:`）
- [ ] 每步**预期输出的字面串**（手册写 `[OK  ]` 而实际 `[OK]` 就会让人以为失败）
- [ ] 失败分支的**提示语**（手册引号里的话必须是代码里真有的串，否则一线 grep 不到）
- [ ] **落盘字段**（`farm_root` / `baseline_setup` / `security.tools_dir` 是否真写进 `config.local.yaml`）
- [ ] **套件名单**与 `hall_auto/suites.py::SUITES` 一致
- [ ] **前置条件清单覆盖了所有"新机上会缺"的项**（这一条最容易漏，因为它不在代码里，在现实里）
      —— 尤其：**pip 源 / 外网**（第 2 步要联网）、**磁盘空间**（盘满的报错长得像"共享盘坏了"）。
      判据：拿一台**真的裸机**过一遍清单，凡是清单没提、又确实会卡住的，就是漏项。
- [ ] **桌面/分发副本同步了**：跑 `tools/sync_handbook.py`（`--check` 能看出旧没旧，rc=1 就是旧了）。
      **手工拷的副本一定会漂，而且不会报错** —— 2026-09-21 真发生过：桌面那份还停在 09-18 的
      「10 步版」，仓库已经是「12 步版」，差了整整三轮修复（含 6 个硬阻断）。
      漏的代价是测试同事拿着旧手册，踩的正是已经修好的坑。
- [ ] **默认值**（新机 `installer_dir` 落哪、包占多少空间、闸门默认开还是关）

后四项已有常驻回归测试守着（`tests/unit/test_bootstrap_policy.py` 末尾两个 drift 用例 +
`test_farm_control_policy.py`），改代码后跑 `tests/unit` 就会红。
