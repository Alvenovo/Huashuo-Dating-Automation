## 一、跑之前必须满足的前置条件

### A. 两侧都要做（**最容易漏，漏了就白干**）

- [ ] **代理 / VPN / 加速器全部关掉，TUN 模式尤其要关。**
  这是 2026-09-22 花了半天才定位的根因，见第四节。**"关掉 TUN 开关"不等于关干净**：
  内核进程可能还在，虚拟网卡可能还在。
  ```powershell
  tasklist | findstr /i "clash mihomo v2ray sing-box verge"
  ipconfig /all | findstr /i "198.18 Mihomo Tunnel"
  ```
  两条都**应该什么都没有**。`ipconfig /all` 里出现 `Mihomo / Meta Tunnel / 198.18.0.1`
  就说明 TUN 虚拟网卡还挂着 —— 它会劫持名字解析，SMB 直接连不上。
- [ ] **两台机器同一个局域网、同一个 SSID**，AP 没开客户端隔离（访客 Wi-Fi 一律不行）。
- [ ] **一律用机器名，不用 IP**：DHCP 换 IP 后报「系统错误 67 找不到网络名」。
- [ ] **时间别差太多**（同一台域控制器/工作组的 NTLM 对偏差敏感）。

### B. 控制机（`LAPTOP-VS5F7HF4`）侧

- [ ] **常开、不休眠、不关屏**。它是唯一的包来源，官方没有下载地址，**没有兜底**。
  bootstrap 第 13 步会设（`tools/set_keep_awake.ps1`），但**顺手确认网卡没被节能关掉**
  （设备管理器 → 网卡 → 电源管理 → 取消「允许计算机关闭此设备以节约电源」）。
- [ ] **445 放行，且规则作用于当前网络配置文件**：
  ```powershell
  netsh advfirewall firewall show rule name=HallShare-SMB
  netsh advfirewall show currentprofile
  ```
  规则应为「已启用 / 入站 / TCP / 本地端口 445 / 操作 允许 / 配置文件 专用,公用」。
  ⚠️ **规则只覆盖「专用,公用」** —— 控制机网络一旦被判成「域」，445 就不放行了。
  ⚠️ 共享盘建好后按遗留项**关掉这条规则**是暴露面控制，**但下次跑批前必须开回来**
  （`tools/provision_share.ps1` 是幂等的，重跑一次即可，别靠记性）。
- [ ] **`hallshare` 账号启用、密码永不过期，且与各节点的 `farm_node.env` 完全一致。**
- [ ] ⚠️ **排障期间建议临时关掉账户锁定**（**跑完恢复**）：
  ```powershell
  net accounts                      # 看现状（当前：阈值 10 次 / 锁 10 分钟 / 窗口 10 分钟）
  net accounts /lockoutthreshold:0  # 排障期间关掉
  net accounts /lockoutthreshold:10 # 跑完改回来
  ```
  理由见第五节：密码一不匹配就锁 10 分钟，**你每试一次就再锁 10 分钟**，
  排障会卡在"等一下再试"上，而且报错从"密码错"变成"账户已锁定"，方向全歪。
- [ ] **共享盘内容就位**：两个安装包、`fixtures/7z2602-x64.exe`、`fixtures/security_tools/`（4 个文件）、
  `wheelhouse/`（cp312）。详见《运行手册.md》「共享盘当前内容」。
- [ ] **密码轮换后必须清客户端的旧映射和旧凭据**（见第五节）—— 否则旧密码会被反复重试。
- [ ] ⚠️ **控制机自己投任务时，`farm_root` 用本地路径，别走 UNC**（2026-09-22 实测）：
  控制机走 `\\<自己>\hall-farm` 用的是**当前登录身份**，而 `hall-farm` 的**共享级权限只给
  `Everyone` 读**（`provision_share.ps1:128`），只有 `hallshare` 是 `Change`（同文件 `:225`）——
  于是 `dispatch` 写 `tasks\` 撞 `PermissionError [Errno 13]`，而 `status` 只读所以能过。
  **提权也没用**（共享级按身份算，管理员同样只匹配 `Everyone`）。
  解法：控制机 `farm_root: C:\hall-farm`（不走 SMB，只受 NTFS 管，本机身份可写）；
  或 `net use \\LAPTOP-VS5F7HF4\hall-farm /user:hallshare <密码> /persistent:yes`（重启后可能失效）。

### C. 测试机（节点）侧

- [ ] **管理员窗口里，先设 3 个环境变量，再跑 bootstrap**。顺序反了变量全丢。
- [ ] **新机的第一个网络动作是 `net use` 认证共享盘**（NTFS 只授权 `hallshare`，
  本机账号在网络上是"别人"）。见《多机代码分发.md》。
- [ ] **真人登录进桌面，不锁屏、不息屏、不断 RDP**（锁屏后截图全黑、点击无落点）。
- [ ] **Python 3.12 64 位 + 在 PATH 里**（共享盘离线 wheel 是 `cp312`）。
- [ ] 磁盘可用空间：手册口径 ≥3 GB，**实测建议 ≥20 GB**（两个包 780MB + 缓存 + 7-Zip）。

### D. 推荐动作顺序（**能绕开 1219，见第五节**）

1. 清干净代理/TUN（两侧）。
2. **先在测试机上手工认证共享盘**，把映射建好：
   ```powershell
   net use \\LAPTOP-VS5F7HF4\hall-packages /user:hallshare "<共享盘密码>" /persistent:yes
   net use \\LAPTOP-VS5F7HF4\hall-farm     /user:hallshare "<共享盘密码>" /persistent:yes
   ```
3. 再跑 bootstrap —— 第 7 步的探针会命中「已可达（无需再连）」，
   **根本不会再发那条会撞 1219 的 `net use`**。

## 二、SMB 错误码速查

| 报错 | 真因 | 怎么修 |
|---|---|---|
| **系统错误 53**「找不到网络路径」 | **代理/TUN 劫持**（最常见，2026-09-22 实证）或网络真不通 | 关 TUN 后重试；`ping -4 <控制机名>` |
| **系统错误 67**「找不到网络名」 | 配置里写了 **IP**，DHCP 换过地址；或共享名写错 | 改回机器名 |
| **系统错误 1219**「同一用户不能用多个用户名连同一服务器」 | 已经有一条到该服务器的会话（**多半是隐式会话**，`net use` 看不到），脚本再换 `hallshare` 去连 | `Restart-Service LanmanWorkstation -Force`，然后**先手工 `net use` 再跑 bootstrap** |
| **系统错误 1909**「引用的帐户当前已锁定」 | `hallshare` 被锁（反复认证失败撞阈值） | 等锁定窗口过（当前 10 分钟）；排障期把阈值设 0 |
| **系统错误 1326**「用户名或密码错误」 | 密码不对，**或用了旧密码**（映射/凭据里还留着上一版） | 核对 `farm_node.env`；清 `net use` + `cmdkey` |
| **系统错误 5**「拒绝访问」 | 用的**不是 `hallshare` 账号**（NTFS 只授权它） | 按上面命令显式带 `/user:hallshare` |
| **系统错误 64**「指定的网络名不再可用」 | 共享被删/服务停了/控制机睡了 | 检查 `net share`、控制机电源 |

**报错原文是英文的**（`net use` 不走中文包），脚本日志里会带 `rc=` 和原文片段 —— 对照本表。

## 三、排障顺序（4 条命令定位）

在**测试机**上（管理员 PowerShell）：

```powershell
Get-SmbConnection                        # ① 当前 SMB 连接 + 用的是谁的身份（关键）
net use                                  # ② 只列显式映射（看不到隐式会话！）
cmdkey /list                             # ③ 凭据管理器里有没有旧密码
Test-NetConnection LAPTOP-VS5F7HF4 -Port 445   # ④ 端口通不通
```

- ① 里出现 `\\LAPTOP-VS5F7HF4` 但 `UserName` **不是 `hallshare`** → 隐式会话坐实，走 1219 的解法。
- ② 空 **不代表没有会话**（这是最容易误判的一点）。
- ③ 有该服务器的条目 → 删掉：`cmdkey /delete:<按 /list 显示的目标>`
- 清隐式会话（**1219 的解药**）：
  ```powershell
  Restart-Service LanmanWorkstation -Force
  Get-SmbConnection                        # 复核：应该空了
  ```
  嫌麻烦就直接重启机器 —— 一次把隐式会话和 10 分钟锁定窗口都耗掉。

## 四、根因：代理/TUN 会让 `\\机器名` 解析不到

2026-09-22 实测链条：

1. 测试机跑 bootstrap → 第 7 步「共享盘连接」两个共享**都**报 **53**，第 9 步农场目录 `[FAIL]`。
2. 控制机上查：共享在、445 在监听、防火墙规则启用且作用域覆盖当前配置文件 → **主机侧没问题**。
3. 控制机上发现 **Clash Verge 在跑，TUN 模式**：虚拟网卡 `Mihomo / Meta Tunnel`，IP `198.18.0.1`，
   假 IPv6 网关 `fdfe:dcba:9876::2`。
4. **两侧关掉 TUN → 53 立刻消失**，换成 1219（第二层问题）。因果确认。

机制：TUN 模式接管路由与 DNS（fake-ip）。`\\LAPTOP-VS5F7HF4` 的名字解析被劫持后拿到的是
不可达的假地址，SMB 在"名字解析/端口"这一层就断，报 **53** ——
**它长得像"共享盘坏了/防火墙挡了"，实际是代理**。这就是为什么 53 必须先查代理再看网络。

⚠️ **控制机自己也装代理不代表不能当包源** —— 关键是**跑批时别开 TUN**。
（同一台机器上 TUN 关掉之后，共享与 445 一切正常，已验证。）

## 五、机制：1219 是脚本自己的探针招来的

`tools/bootstrap_machine.py` 的 `_share_connect`（约 540 行）顺序是**先探后连**：

1. `share_reachable()` → 里面就是 `directory.is_dir()`，**直接访问 UNC**。
   这一步用的是**当前 Windows 登录身份**（测试机的 `admin`），会在服务器上建一条 SMB 会话。
2. 紧接着 `net use ... /user:hallshare` → 服务器拒绝："同一服务器不能换用户名" → **1219**。

**`net use` 只列显式映射，看不见这种隐式会话** —— 所以「`net use` 是空的」和「有 1219」
可以同时成立，这不是矛盾，是证据。

**脚本已按这条修（2026-09-22）**：`_share_connect` 命中 1219 时先按**同一个 target** `/delete`
再重试一次；仍失败就打出「跑一次 `Restart-Service LanmanWorkstation -Force`」这句下一步，
不再只丢一句 `rc=2` 让人猜。

配套坑：`net use ... /persistent:yes` 建的映射会**带密码持久化**。
**密码轮换之后，旧映射会自动重连、拿旧密码反复认证 → 撞满阈值 → 锁账号（1909）。**
所以轮换密码时，两侧都要清：

```powershell
net use * /delete /y
cmdkey /list        # 有目标服务器条目就 cmdkey /delete:<目标>
```

## 六、pathlib 在 UNC 上的吞错规则（**实测，写代码必看**）

`Path.is_dir()` / `is_file()` **不是一律吞错**，规则很具体：

```python
_IGNORED_ERRNOS    = (ENOENT, ENOTDIR, EBADF, ELOOP)
_IGNORED_WINERRORS = (21 ERROR_NOT_READY, 123 ERROR_INVALID_NAME, 1921 ERROR_CANT_RESOLVE_FILENAME)
```

命中就返回 `False`，**没命中就原样重抛**。2026-09-22 在本机实测：

| WinError | 映射到的 errno | `is_dir()` 行为 |
|---|---|---|
| 53 ERROR_BAD_NETPATH | 2 ENOENT | **吞成 `False`** |
| 67 ERROR_BAD_NET_NAME | 2 ENOENT | **吞成 `False`** |
| 1909 ERROR_ACCOUNT_LOCKED_OUT | 13 EACCES | **重抛 → 崩** |

**结论：UNC 上的存在性判断必须 catch `OSError`。** 只 catch 一部分（比如只包了 `mkdir`）
就会出现"同一个故障，一处报 `[FAIL]`、另一处直接 traceback"——
2026-09-22 的 bootstrap 崩溃就是这么来的：`step_farm_root` 包了 `mkdir` 没包 `is_dir()`，
53 那次干净失败，1909 这次整个脚本崩掉，**后面 4 步全没跑、报告 JSON 也没写**。

**已修（2026-09-22）**：`step_farm_root` 把 `is_dir()` 和 `mkdir()` 一起包住；
共享盘 wheelhouse 的同类调用也包了。守卫在 `tests/unit/test_bootstrap_policy.py`
（注入法验过能红）。

同一类教训在本项目已经出现过两次（`Path.is_file()` 吞 `OSError` 报假平安、
`step_share_login` 两条都连不上仍打 `[OK]`）。**凡是落在 UNC 上的文件系统调用，
一律当成会抛异常来写，并且失败要能被结果行看见。**
