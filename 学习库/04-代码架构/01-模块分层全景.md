# 01 · 模块分层全景

> 前面讲"为什么这么设计"，这里讲"代码怎么落地的"。**18 个模块，约 6900 行（含测试）。**

## 模块全景

```
hall_auto/                       测试框架层（被测对象无关的通用能力）
├── config.py        配置加载     YAML + 本地覆盖 + 冻结 dataclass
├── waiting.py       等待         wait_until 条件轮询
├── winapi.py        Win32 封装   EnumWindows / WM_GETTEXT / BM_CLICK
├── screen.py        截图        虚拟屏抓取 + 红像素计数 + 平均亮度
├── evidence.py      证据留痕     终态截图 + result.json + report.html
│
├── product.py       产品状态     注册表 / 文件版本 / 进程（纯系统读取）
├── version.py       版本计算     文件名解析 / 版本比较（纯函数）
├── installer.py     安装层       装/卸/升级 + 版本等待
│
├── launch.py        启动就绪     前置窗、白名单弹窗、结构就绪判定
├── search.py        搜索详情     搜索框操作、命中过滤、详情页定位
├── apps.py          应用装卸     「我的」页三列表 + 厂商向导 + NSIS
├── login.py         账号         登录/短信/忘记密码/微软（跨窗口按 pid）
├── register.py      注册         格式校验 + 红像素反馈判定
├── settings.py      设置         主题三档 + 亮度断言
├── about.py         关于页       版本节点 OCR
├── security.py      安全验证     签名工具 + 清单对比
└── entries.py       入口         首页入口区域定位 + WB 入口

tests/
├── conftest.py      夹具 + 标记门禁 + 证据钩子
├── unit/            9 个文件，101 条，纯逻辑，毫秒级
├── install/         P0-01/02，需管理员
└── launch/          P0-03~07 + P1 + P2，需起客户端

tools/               探针（不属于测试框架）
├── probe_uia.py     大厅 UIA 树
```

## 分层原则

| 层 | 模块 | 特征 | 测试方式 |
|---|---|---|---|
| **纯逻辑层** | `version.py` | 纯函数，无 IO | 单测，毫秒级 |
| **系统读取层** | `product.py` | 只读系统，不起 UI | 单测（只读断言） |
| **动作层** | `installer.py` `launch.py` `search.py` `apps.py` `login.py` | 操作被测对象 | 集成用例，需环境 |
| **编排层** | `conftest.py` | 夹具、门禁、钩子 | 无（框架代码） |

> [!important] 这个分层最值得学的地方
> **`version.py` 被单独抽出来做纯函数**，因此能用 101 条毫秒级单测覆盖。
>
> 对比另一种写法：把版本解析内联在 `installer.py` 里 → 要测它就得**装一次包**（几分钟 + 提权）。
> **同样一段逻辑，抽成纯函数后测试成本下降三个数量级。**
>
> **可迁移的做法：凡是不依赖 UI/IO 的判断逻辑，全部抽成纯函数单独测。**

## 关键函数地图

### `version.py`（纯计算，测试覆盖率最高的地方）

| 函数 | 作用 |
|---|---|
| `expected_version_from_setup_name(filename)` | 从文件名取 `1.6.8.17S` → 去 `S` → `1.6.8.17` |
| `parse_dotted_version(text)` | 字符串 → 四元组 |
| `versions_equal(actual, expected)` | **字符串相等**（不要只比前三段） |
| `four_segment(version)` | 补齐四段 |

### `product.py`（系统状态 oracle）

| 函数 | 作用 |
|---|---|
| `is_admin()` | 是否管理员（提权判断的入口） |
| `read_installed()` | 读注册表 → `InstalledProduct`（含安装目录、卸载串、版本） |
| `_file_version(path)` | 读 exe 的 `FileVersion` |
| `read_agreen()` / `set_agreen()` | 隐私协议状态（可复现未同意态） |
| `stop_product()` | 杀进程（含重试与超时） |

### `launch.py`（最容易出问题的模块，452 行）

| 函数 | 作用 |
|---|---|
| `_overlay_windows(...)` | 枚举**覆盖在主窗之上的窗口**（弹窗检测核心） |
| `is_whitelisted(name, settings)` | 白名单判断（协议/权限/更新） |
| `is_unknown(overlay, settings)` | **未知弹窗判定** → 触发失败 |
| `dismiss_whitelist_popups(...)` | 自动关闭白名单弹窗 |
| `_back_if_subpage(main)` | 恢复上次页面陷阱的修复 |
| `_structure(main, settings)` | 就绪结构判定 → 返回 (结构集合, 是否就绪) |
| `concrete_main(pid, title_contains)` | 登录态句柄失效的解法 |
| `wait_until_ready(cfg, main)` | 就绪循环（含 handle/pid 缓存） |

### `apps.py`（最大模块，757 行，风险最高的地方）

| 函数 | 作用 |
|---|---|
| `open_mine(main)` | 进「我的」页 |
| `switch_app_tab(main, tab)` | 切三个页签 |
| `read_mine_lists(main)` | 读三个列表状态 |
| `installed_display_names()` | 读系统卸载注册表（oracle） |
| `match_display_name(app_name, names)` | **大厅商品名 vs 注册表名**的匹配 |
| `find_item_button(main, app_name, action_aid)` | 找条目内的操作按钮 |
| `is_installer_dialog(hwnd, app_name)` | 判断是否厂商安装器对话框 |
| `installer_pids(app_name)` | 找安装器/卸载器进程 |
| `wizard_buttons(hwnd)` | Win32 读按钮文字 + 矩形 |
| `pick_wizard_button(buttons, drawn_ok)` | 选按钮（含自绘按面积） |

### `login.py`（444 行，跨窗口操作的代表）

| 函数 | 作用 |
|---|---|
| `_windows(pid)` / `_nodes(pid, ...)` | **按 pid 跨窗口**找控件（不绑主窗） |
| `logged_in(pid)` | 登录态判定 |
| `_check_agree(pid)` | 勾协议（不勾登录按钮是灰的） |
| `request_sms_code(...)` / `login_with_sms_code(...)` | 短信（人在环） |
| `open_forgot_password_page(...)` / `submit_forgot_reset(...)` | 忘记密码往返 |
| `microsoft_pick_account(...)` / `wait_microsoft_logged_in(...)` | 微软 SSO |

## 代码里的"约定优于配置"

| 约定 | 体现 |
|---|---|
| 破坏性操作必须门禁 | `conftest._allow_install()` 统一判断 |
| 敏感信息只走环境变量 | `config.test_account()` 读 `HALL_TEST_USER/PASSWORD` |
| 配置缺失则 skip | `UpdateFixture.configured()` / `SecuritySettings.configured()` |
| 证据自动留痕 | `conftest.pytest_runtest_makereport` 钩子 |

> [!tip] 这些约定为什么放在 conftest / config 而不是各用例里
> **因为它们是横切关注点（cross-cutting concern）**：门禁、凭据、证据，每个用例都需要。
> 集中一处 → 改一次全生效 → 不会有人漏写。
> **反例：如果每个用例自己判断 `if HALL_TEST_USER:`，迟早有人忘了写，导致用例在没凭据时"看似通过"。**

## 自测

> [!question]- Q1：为什么 `version.py` 只有 4 个函数，却是单测最多的模块？
> 因为它是**所有版本断言的公共地基**，错一点就全线假失败；而且它**满足纯函数条件**（无 IO、无状态），测试成本极低。
> **投入产出比最高的测试对象 = 被广泛依赖的纯逻辑。**

> [!question]- Q2：`launch.py` 有 452 行，却只做"把窗口等到就绪"这一件事，为什么这么复杂？
> 因为它要处理大量**被测对象的异常路径**：
> 前置权限窗、白名单弹窗、未知弹窗、恢复上次页面、结构判定、句柄缓存、登录态重包……
> **这些复杂度不是设计出来的，是从产品现实里"喂"出来的。**
> 对比：如果产品启动永远干净，这个模块大概只要 50 行。

> [!question]- Q3：`apps.py` 里为什么需要 `match_display_name` 这样一个函数？
> 因为**大厅商品名和注册表 DisplayName 不是一个东西**：
> - 列表里：`7-Zip（64位）`
> - 注册表：`7-Zip 26.02 (x64)`
>
> 断言"装上了"要拿注册表条目比对，但列表里给的名字与之不同 → 需要**模糊匹配**（`registry_hint` 配置）。
> **教训：同一个实体在不同系统里有不同名字，跨系统断言必须有映射层。**

> [!question]- Q4：`conftest.py` 里的横切关注点集中，有什么风险？
> 集中化的风险是**"一处出错，全局受影响"**。例如证据钩子写错，所有用例的报告都有问题。
> 所以这类代码要特别注意：
> ① 钩子内部不能抛异常（会污染用例结果）
> ② 要能降级（截图失败不该让用例失败）
>
> 本项目 `evidence.py` 的 `capture_screen` 返回 `bool`，失败时不抛 —— 这是**正确的降级设计**。

> [!question]- Q5：`tools/` 为什么不放进 `hall_auto/` 或 `tests/`？
> 因为定位不同：
> - `hall_auto/` = **测试运行时依赖**（用例会 import）
> - `tests/` = **用例本体**（pytest 收集）
> - `tools/` = **一次性侦察工具**（人工运行，不参与自动化流水线）
>
> 混淆会导致：探针脚本被 pytest 误收集、或者生产路径依赖了只该用于调试的代码。
> **目录结构本身就是一种架构表达。**
