# 03 · 等待机制演进

> **UI 自动化的核心难题之一：怎么知道"可以开始了"。**
> 这条记录了一个从 `sleep` 到条件轮询的真实演进，以及一个性能坑的根因。

## 演进路线

```
第一代：固定 sleep
    time.sleep(3)
    ❌ 慢机器不够，快机器浪费；而且失败时无法解释

第二代：固定 sleep + 重试
    ❌ 仍然靠猜时间

第三代：条件轮询（本项目采用）
    wait_until(predicate, timeout_sec, interval)
    ✅ 条件满足立刻返回，超时才失败
```

## `waiting.py` 的实现

```python
def wait_until(predicate, timeout_sec=10.0, interval=0.3) -> bool:
    """轮询直到 predicate 为真，或超时。"""

def wait_until_or_raise(predicate, timeout_sec, interval, message):
    """同上，但超时抛异常并带上 message（便于归因）。"""
```

**特点**：默认间隔 **0.3s** —— 足够灵敏，又不会把 CPU 打满。

> [!important] 条件轮询的额外好处
> 它让**失败变得可解释**。超时失败时，你知道的是"**这个条件在 N 秒内一直不成立**"，而不是"睡了 3 秒后它还不满足"。
> 前者是明确的判据，后者是模糊的断言。
> 而且 `predicate` 本身通常就是**产品判据**（如"结构齐全"），所以失败信息天然有意义。

## 但是——轮询里藏了个性能坑

**原始问题**：就绪循环跑得很慢，"首页停留过长"。

**根因排查**（这是本条的精华）：

```
怀疑方向 1：轮询间隔太大？
   → 改小 → 略快但没解决

怀疑方向 2：条件判断本身太慢？
   → 加计时 → 发现 main.handle 单次约 1s

真相（二次根因）：
   就绪循环里每轮都重新读 main.handle 和 main.element_info.process_id
   这两个值在窗口生命周期内是不变量，但每次读取约 1s
   3 轮循环 × 2 个值 ≈ 6 秒白等
```

**修法**：

```
❌ 循环内每轮取
   for ...:
       h = main.handle              # ~1s
       pid = main.element_info.process_id   # ~1s

✅ 循环外取一次，缓存后传入
   h = main.handle                  # 只在外面取一次
   pid = main.element_info.process_id
   for ...:
       use(h, pid)
```

**对应 commit**：`3f661bf` / `60b5bfb`（"等待机制 sleep→条件轮询、首页停留长根因修复（就绪循环重构 + handle/pid 缓存）"）

## 可迁移的三条经验

> [!tip] 经验 1：UI 自动化里的"读取"不是免费的
> `main.handle`、`element_info.process_id`、`descendants()` 这类操作**都是跨进程调用**，动辄百毫秒到秒级。
> 在循环里重复读，就是**用秒级操作乘以循环次数**。
> **排查"为什么慢"的第一步：找循环里的重复昂贵调用。**

> [!tip] 经验 2：区分「不变量」和「易变值」
> | 类型 | 例子 | 处理 |
> |---|---|---|
> | 窗口生命周期内不变 | `handle`、`pid` | **循环外取一次** |
> | 每次都可能变 | 控件是否存在、文本内容 | 循环内取 |
>
> 判断错了方向，就会得到"缓存了易变值导致假通过"或"重复读不变量导致慢"。

> [!tip] 经验 3：优化前先测量
> 如果直接猜"间隔太大"，改 0.3 → 0.1，收益微乎其微（因为瓶颈在别处）。
> **先加计时找出真瓶颈，再改。** 否则就是"用猜测代替测量"，很容易白忙。

## 等待的层次

本项目里有多种"等待"，粒度不同：

| 层次 | 位置 | 等什么 |
|---|---|---|
| 进程级 | `product.stop_product()` | 进程真的退出 |
| 窗口级 | `launch.wait_main_window()` | 主窗口出现 |
| 就绪级 | `launch.wait_until_ready()` | 结构齐全（**含多次冷启动**） |
| 控件级 | `login.switch_login_tab(pid, kw, ready=...)` | 页签切换后控件就位 |
| 状态级 | `apps.app_list_state(main, tab, timeout)` | 列表刷出数据 |
| 系统级 | `installer.wait_version(expected, timeout)` | 注册表版本稳定 |

> [!important] 层次化等待的价值
> 每一层只等**它真正需要的条件**，而不是笼统地"等 3 秒"。
> 好处：
> ① 失败信息精确（是窗口没起还是结构没齐？）
> ② 各层可独立调优超时（`config.yaml` 的 `timeouts` 就是按层给的）
> ③ 快机器上不浪费时间

## 自测

> [!question]- Q1：为什么固定 `sleep` 在 UI 自动化里是坏实践？
> 三个原因：
> ① **慢机器不够** → 偶发失败，难复现
> ② **快机器浪费** → 累积起来拖慢整个套件
> ③ **失败不可解释** → 超时后你不知道是"条件不满足"还是"等得不够"
>
> 条件轮询同时解决这三点。

> [!question]- Q2：`main.handle` 为什么读一次要 1 秒？
> 因为它是**跨进程查询**：pywinauto 要通过 UIA/Win32 去问目标进程的窗口信息。
> 这类调用不像读 Python 变量，代价在毫秒到秒级。
> **认知：在 UI 自动化里，"属性访问"可能是昂贵操作。**

> [!question]- Q3：如果条件轮询的 `predicate` 本身很慢（如每次要遍历整棵树），怎么优化？
> 思路和 `handle` 那个坑一样，分两步：
> ① **看能否缩小查询范围**（只查某个子树而不是整棵树）
> ② **看能否缓存不变量**（树里静态的部分只取一次）
> 另外可以**适当加大 `interval`** —— 如果 predicate 要 1s，那 0.3s 的间隔没意义，轮询本身就成了瓶颈。

> [!question]- Q4："先测量再优化"在这条演进里怎么体现？
> 如果当初直接猜"间隔太大"，改成 0.1s：3 轮 × 2 次 × 1s 的**主要成本完全没变**，几乎没有改善。
> 加计时后发现瓶颈在 `handle` 读取 → 一改就对。
> **优化顺序：测量 → 定位 → 改一个变量 → 再测量。**

> [!question]- Q5：为什么"等待"要分这么多层次，而不是写一个大 `wait_ready(max=150s)`？
> 因为一个笼统的长等待**丢失了归因信息**：超时后你不知道卡在哪一步。
> 分层后：窗口级超时 → 产品启动问题；结构级超时 → 首页渲染问题；列表级超时 → 接口问题。
> **分层等待 = 分层归因。**
