# 04 · 证据留痕机制

> **自动化失败时，最有价值的不是"失败了"这个结论，而是"当时屏幕上是什么"。**
> 这条机制解决的是"跑完一轮，怎么向别人证明发生了什么"。

## 产物结构

```
reports/evidence/<日期_时间>/
├── report.html                    # 自包含单文件，可直接发组长
├── <模块>/<用例名>/
│   ├── final.png                  # 用例终态截图
│   └── result.json                # 结构化结果
```

**特点**：`report.html` 把截图 **base64 内嵌**，**单文件自包含** —— 发给别人不用带附件目录。

## 工作流程

```
pytest 跑批
   ↓
conftest 挂载钩子（pytest_runtest_makereport）
   ↓
每个用例结束（通过/失败/skip）→ evidence.record(nodeid, outcome, duration, assertion, title)
   ↓
sessionfinish → evidence.finish() → 生成 report.html
   ↓
prune_old_runs(keep_days=30)  → 清理过期 run
```

## 关键设计点

### ① 开关：`--evidence=all` / `failure-only`

| 模式 | 行为 | 适用 |
|---|---|---|
| `all`（当前默认） | 所有用例都截图 | 调试期，看全貌 |
| `failure-only` | 只在失败时截图 | 日常回归，省空间 |

> [!tip] 为什么默认是 `all` 而不是 `failure-only`
> 因为机制刚落地时，**需要先验证"它到底能不能用"** —— 只有全量截图才能看清每步的终态。
> **待办里明确写了**：*「你人工回看几轮确认证据机制可行后，把 `--evidence` 默认从 `all` 改 `failure-only`（只改 `tests/conftest.py` 一处）。」*
>
> **这是很务实的做法：新机制先全量观察，确认可靠后再收紧。** 而不是一上来就按"最优配置"上线，结果出问题看不到证据。

### ② 保留期：`--evidence-keep-days=30`（0 = 不清理）

**为什么需要**：截图很占空间（示例里一个 run 有 **89MB**）。

### ③ 报告里的信息层次

| 列 | 内容 | 来源 |
|---|---|---|
| 用例名 | 模块/文件名 | `nodeid` |
| **中文说明** | **取 docstring 首行** | 用例的 docstring |
| 结果 | 通过/失败/skip + **行级配色** | `outcome` |
| 断言 | 关键断言文本 | `_assertion_text(report)` |
| skip 原因 | **按 marker 分类 + `pytest.skip()` 原文** | `_skip_label(item, report)` |
| 终态 | 截图（内嵌） | `capture_screen` |

> [!important] 「中文说明取 docstring 首行」这个设计很聪明
> 因为用例名是英文（`test_p0_04_ready_cold_starts`），**组长和产品看不懂**。
> 而每个用例的 docstring 首行本来就是中文业务描述（如 `"""P0-04 冷启动稳定性：连续冷启动多次，首页结构每次完全一致"""`）。
>
> **一行代码就把技术报告翻译成了业务报告**，不需要额外维护映射表。
> **可迁移：让"技术标识"和"业务描述"在源码里就近放置，报告层自动提取。**

### ④ skip 原因要分类

**为什么**：skip 的原因五花八门，混在一起看不出问题。

| skip 类型 | 含义 | 需要行动吗 |
|---|---|---|
| 缺凭据 | `HALL_TEST_USER` 没设 | 配环境变量 |
| 未提权 | 需要管理员 | 走计划任务 |
| 配置缺失 | `fixture_apps.*` 为空 | 补配置 |
| 非交互终端 | 人在环用例在代理侧跑 | 在自己终端跑 |
| 前提不满足 | WB 已安装等 | 正常 |

**分类后，一眼能看出"这轮有多少 skip 是因为环境没准备好"**，而不是笼统的"N skip"。

## 已知的待完善点

| 问题 | 现状 | 解决方向 |
|---|---|---|
| 「关键断言」列对**通过的用例为空** | 因为只有失败报告里有断言文本 | 要上**步骤级 `step("...")` 显式记录** |
| unit 纯逻辑用例也截图，很吵 | 默认 `all` 模式 | 在 conftest 按 marker 排除 |
| 改 docstring 后报告不刷新 | 报告读的是运行时的 docstring | 重跑一轮才更新 |
| 样例 run 占 89MB | `reports/evidence/2026-09-17_1052/` | 看过可删 |

> [!important] 这份"待完善点"清单本身就是好实践
> 它明确区分了**已经能用**和**还不够好**，并且每条都给了解决方向。
> **不是"证据机制完成了"，而是"证据机制 v1 落地，这些是 v2 的方向"。**
> 这种诚实的记录方式，比宣称"机制完善"有用得多。

## 一句话总结这个机制的价值

> [!tip]
> 自动化的信任问题：**别人凭什么相信你的结论？**
> 答案：**每一条结论都附带当时的原始证据（截图 + 断言文本 + 环境信息），且报告能独立传播。**
>
> 没有证据留痕的自动化，失败时会被质疑"是不是脚本的问题"；有证据留痕，讨论就能直接聚焦到产品。

## 自测

> [!question]- Q1：为什么报告要做成"自包含单文件"？
> 因为**传播场景**：要发给组长/开发看。
> 如果是 HTML + 图片目录，接收方必须完整解压、路径不能错、邮件不能丢附件……任何一环出问题就看不了。
> base64 内嵌后，一个文件搞定。**代价是文件变大，收益是零摩擦传播。**
> **设计产物时，先想"谁在什么场景看它"。**

> [!question]- Q2：`--evidence` 默认从 `all` 改 `failure-only` 为什么要等"人工回看几轮"？
> 因为**新机制的可信度需要先用全量数据验证**。
> 如果一上线就是 `failure-only`，那么"通过的用例到底截了什么"没人看过 → 万一截图逻辑有 bug（比如截错窗口），不会有任何反馈。
> **先全量观察，再按需收紧 —— 这是新能力上线的通用节奏。**

> [!question]- Q3：为什么"关键断言列对通过的用例为空"是个要解决的问题？
> 因为**对通过的用例，也需要知道"它到底验了什么"**。
> 只知道"P0-06 通过了"，不知道"验了几条命中、命中哪几个词"，报告的信息量就少了一半。
> 解决方向是 `step("...")` 显式记录步骤级信息 —— 把断言过程也变成证据。
> **目标：报告不仅回答"过没过"，还回答"验了什么、依据是什么"。**

> [!question]- Q4：为什么要按 marker 分类 skip 原因？
> 因为**不同 skip 原因的行动方不同**：
> - 缺凭据 → 我配环境变量
> - 未提权 → 我走计划任务
> - 配置缺失 → 我补配置
> - 非交互终端 → 正常，不用管
>
> 不分类的话，只能看到一个 skip 数字，无法行动。
> **报告的价值 = 能否直接驱动下一步动作。**

> [!question]- Q5：如果让你给这个机制加一个功能，你会加什么？
> 参考思路：
> - **失败时的"对比证据"**：不只截终态，还截预期状态（如上次通过的截图）
> - **环境快照**：把这轮的 `admin=True/False`、版本号、配置摘要写进报告头
> - **失败聚类**：多轮跑批后自动发现"这条用例最近 5 轮失败 4 次"（区分偶发与真缺陷）
>
> 方向都是同一个：**让报告回答更多"为什么"，而不只是"是什么"。**
