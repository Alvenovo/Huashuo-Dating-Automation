# 02 · 配置与数据夹具化

> 原则 4 的落地：**线上运营一变，只改配置，不改脚本结构。**

## 双层配置文件

```
config.yaml           ← 进 git，本机无关的默认值
config.local.yaml     ← 已在 .gitignore，本机/凭据相关覆盖
```

**合并方式**：`_deep_merge(base, overlay)` —— 深度合并，本地覆盖基线。

> [!important] 为什么要分两层
> | 需求 | 解决方式 |
> |---|---|
> | 团队共享默认配置 | `config.yaml` |
> | 每台机器路径/超时不同 | `config.local.yaml`（不进 git） |
> | 凭据不能落盘 | **只走环境变量**（连 local.yaml 都不放密码） |
>
> 注意第三行：**凭据比 local.yaml 还要更严**。`config.local.yaml` 虽不进 git，但仍是一个文件；密码只走环境变量。

## 配置项分类

### ① 会变的业务数据（夹具化的核心）

```yaml
search_keyword: "qq"           # 搜索词
search_min_hits: 2             # 至少命中几条

fixture_apps:                  # 四个夹具角色
  install: ""
  update: ""
  uninstall: ""
  sync: ""                     # 永久留空（见 02-P1独立套件）

update_fixture:                # 更新夹具的完整定义
  name: ""                     # 大厅商品名
  registry_hint: ""            # 注册表名片段（两个名字不同！）
  pinned_version: ""           # 钉住的起点版本
  package: ""                  # 相对 installer_dir
  sha256: ""                   # 防本地包被换
  url: ""                      # 官方下载地址
  install_dir: ""
  version_exe: ""              # 读版本的 exe
```

> [!tip] 这里有个很细的防护
> `sha256` 字段：**防本地包被换**。
> 因为夹具包是人工下载放在本地的，如果哪天被替换成别的版本，起点就不确定了 → 用例行为漂移。
> **规律：任何"人工准备的外来资源"都应该校验完整性。**

### ② 路径（禁止写死）

```yaml
installer_dir: "C:/Users/ASUS/Desktop/华硕大厅"
baseline_setup: "myappstore_1.6.8.17S_Setup.exe"
latest_setup: "myappstore_1.6.10.7S_Setup.exe"
```

方案原文：**「安装包路径禁止写死。」** 脚本只读配置。

### ③ 超时（按机器调优）

```yaml
timeouts:
  install_sec: 900      # 15 分钟
  uninstall_sec: 300
  version_settle_sec: 180   # 版本稳定等待
  process_stop_sec: 30
  launch_sec: 45
  ready_sec: 90
```

**说明**：「首装初始化慢，本机超时覆盖在 `config.local.yaml`（launch 120 / ready 150），没改入库默认。」

> [!important] 超时值为什么"入库默认"和"本机覆盖"分开
> 入库的默认值代表**通用假设**；本机覆盖代表**这台机器的实测情况**。
> 如果直接把本机的 150 写进默认，别人在更慢的机器上还是会失败，但没人知道该调多少。
> **做法：默认给保守值，实测调优放本地。**

### ④ 就绪判定参数（结构化的判据）

```yaml
launch:
  cold_starts: 3               # 冷启动次数
  required_auto_ids:           # 必备结构三件套
    - SearchBarInput
    - TabList
    - MainWeb
  webview_ready_names:
    - 专题页
  popup_whitelist_keywords:    # 可自动关闭的弹窗关键词
    - 启动卡片
    - 更新
    - 协议
    - 隐私
    - 权限
    - 须知
    - 条款
    - 欢迎使用
  dismiss_buttons: [关闭, 取消, 稍后, 以后再说, 我知道了]
  accept_buttons: [同意, 确定, 允许, 是]
```

> [!important] 这张表最值得学的是「白名单机制」
> 方案不是"识别所有弹窗然后分类处理"，而是**"只有名单内的才敢自动点，名单外一律失败"**。
> ```
> 名单内 → dismiss_buttons / accept_buttons 自动处理
> 名单外 → 未知弹窗 → 失败 + 截图 + 标题/正文
> ```
> **这是安全默认值设计**：白名单机制的安全性是"漏了会失败"，黑名单机制的危害是"漏了就乱点"。
> **在自动化里，永远选"失败"而不是"猜"。**

## `Config` 是个冻结的 dataclass

```python
@dataclass(frozen=True)
class Config:
    ...
    def baseline_path(self) -> Path: ...
    def latest_path(self) -> Path: ...
    def test_account(self) -> tuple[str, str]:   # 读环境变量
    def new_password(self) -> str:                # 读环境变量
```

**特点**：
- `frozen=True` → 加载后不可变，避免用例间互相污染
- 路径用**方法**拼（`baseline_path`），不是存字符串 → 保证 `installer_dir + baseline_setup` 的拼接逻辑只写一次
- 凭据用**方法**读环境变量，不是字段 → **配置对象里根本没有密码**

> [!tip] `frozen=True` 的价值
> 如果配置可变，某个用例改了 `cfg.search_keyword`，后面的用例全受影响，且极难排查。
> 冻结后想改只能新建对象 → **变更显式化**。

## 敏感信息的处理规范

| 信息 | 处理方式 | 理由 |
|---|---|---|
| 密码 / 测试号 / 微软邮箱 | **只走环境变量** | 不落盘、不进 git、不写进任何文件 |
| 内部安全工具路径 | `config.local.yaml` | 工具本身不进公开仓库 |
| 受检安装包 | 本地 `fixtures/` 目录 | 不进公开仓库 |
| 本机路径 | 现状：部分进了仓库（`AGENTS.md`/知识库） | **已知的 open 决策** |

> [!warning] 一个仍未解决的问题
> 项目把本机路径 `C:\Users\admin` 写进了公开仓库的文档。这是个**明确的已知风险**，方案里有记录（"机器路径带 Windows 用户名进公开仓库这个老决策仍 open"）。
> 修法：改 `$PSScriptRoot` / 相对路径，但 P0 安装入口改了要**下轮复跑才算数**。
> **这个条目本身很值得学：承认遗留问题、给出修法和验证条件，而不是假装没有。**

## 自测

> [!question]- Q1：为什么 `config.yaml` 和 `config.local.yaml` 要分开？
> 因为**"团队共享的默认"和"本机特有的覆盖"是两个不同生命周期的东西**：
> - 前者要进 git，所有人一致
> - 后者不能进 git（含本机路径、个人环境）
>
> 如果混在一起，只能二选一：要么把本机路径提交（污染他人），要么每次手动改（容易忘）。

> [!question]- Q2：为什么密码连 `config.local.yaml` 都不放？
> 因为 local 文件**仍然是磁盘上的文件**：会被备份、会被误发、会被聊天工具传出去。
> 环境变量只在进程内存里，**生命周期短、不落盘**。
> **判据：越敏感的信息，允许它存在的"持久化程度"越低。**

> [!question]- Q3：`required_auto_ids` 放在配置里而不是代码里，好处是什么？
> 换版本后如果结构变了，**改配置就能调整**，不用改代码、不用重跑单测、不用走 code review。
> 而且**它把"就绪判据"显式化了** —— 看配置就知道"什么叫就绪"，不用去读 `launch.py` 的实现。
> **配置即文档。**

> [!question]- Q4：白名单机制和黑名单机制，为什么前者更适合自动化？
> | | 漏掉一个 | 后果 |
> |---|---|---|
> | 白名单 | 没在名单里 → 当未知弹窗 | **失败 + 留证**（安全） |
> | 黑名单 | 没在名单里 → 以为是正常的 | **被点击/被忽略**（危险） |
>
> 未知弹窗可能正在问"要不要装某个软件"。自动点它 = 不可控风险。
> **在不确定时失败，是安全设计的第一原则。**

> [!question]- Q5：`Config` 用 `frozen=True` 有什么代价？
> 代价是"想改配置就得新建对象"，写起来麻烦一点。
> 但收益是**用例间零污染** + **变更显式化**。
> 在这个项目里，配置是全局单例（session 级 fixture），**污染风险极高**，所以冻结是对的。
> **反过来：如果配置对象是每个用例各造一个的局部变量，frozen 的收益就小很多。**
