# 04 · 明确不做的边界

> **一个方案的专业度，一半体现在它写了"不做什么"，以及为什么。**
> 这一节是全篇最值得学的部分——不是学结论，是学"怎么论证不做"。

## 不做的清单及理由

| 不做项 | 理由 |
|---|---|
| MuMu / 模拟器、微信小程序宿主 | 安装目录里有这些宿主，但**本期不测**——不是同一个产品线 |
| 控制面板里搜索 QQ | 搜索指的是**大厅内应用目录搜索**，不是控制面板搜索。混淆会导致完全做错 |
| 本机日常软件（微信、WPS、钉钉）当装卸/更新对象 | **高危**。这些是真软件，动了会真改用户机器 |
| 6 个安装包全量升降级矩阵 | 日常只需两条：**当前基线包** + **目录内最新包**。6 包矩阵是**发布可选闸门**，不是日常 |
| 纯图像识别当主定位手段 | 维护成本极高，界面一改就废，失败原因不可解释 |
| 大厅内「自己检测更新」 | 若与 `Setup.exe` 升级**不是同一条路径** → 记为 **P1 候选项**，不进当前 P0 |
| 把 8 个模块串成一条超长脚本 | 失败归因困难 + 迭代慢 + 大部分模块不需要每轮跑 |
| 像素级截图对比主界面 | Banner/活动素材天天变 → 天天假失败 |

> [!important] 最值得注意的三个"不做"
>
> **① 6 包全量矩阵 → 降级为发布闸门**
> 不是"不做"，是"**不在日常做**"。日常只需验证基线包和最新包。这个区分避免了"每次回归跑一小时"。
>
> **② 大厅自更新 → 先探测路径，再决定归属**
> 方案没有拍脑袋说"做"或"不做"，而是给了**判断条件**：如果它和 `Setup.exe` 升级是同一条路径，可以合并；如果不是，另立 P1 候选。
> **这是"信息不足时的正确姿态"——留下判断条件，而不是猜结论。**
>
> **③ 图像识别 → 不当主手段**
> 注意措辞："不当**主**定位手段"，不是完全禁止。实际上 `about.py` 就用了 OCR，但那是**局部兜底**（版本节点 UIA 读不到），不是主路径。
> **"降级为兜底"和"完全禁止"是两回事。**

## 方案还主动"补"了原需求没写的

原需求（组长给的 8 条）里没提，但方案主动补进去了：

| 补充项 | 为什么要补 |
|---|---|
| **首次启动协议弹窗** | 不处理会被当成"未知弹窗"导致 P0-04 失败 |
| **大厅自身卸载** | P0-01 装基线前要腾地方 |
| **UAC / 管理员权限** | 安装和卸载器都需要提权，不处理直接失败 |
| **WebView2 点不到时的受阻口径** | 提前约定"什么情况算受阻而非失败"，避免事后扯皮 |

> [!tip] 这一节的方法论价值
> 需求方给的清单是**从业务视角**写的（"要测搜索、要测登录、要测卸载"）。
> 方案作者的工作是**翻译成工程视角**，并补上：
> ① 需求方的隐含前提（首次启动有什么）
> ② 需求方没想到的工程依赖（提权、WebView2 能力边界）
> ③ 需求与产品实际的偏差（大厅内搜索 vs 控制面板搜索）
>
> **这正是"测试开发"和"执行测试的人"的区别所在。**

## 原需求 8 条的调整对照

| 原项 | 调整后 | 调整理由 |
|---|---|---|
| 1. 控制面板显示版本 | 改注册表 + 文件版本，控制面板只作人工抽检；**并补上「基线安装 + 升最新」** | 减少渲染依赖，同时补齐了更关键的安装路径 |
| 2. 模糊搜索 QQ | 保留，但限定**大厅内**搜索；关键词和期望命中写配置 | 消除歧义 + 配置化 |
| 3. 实时检测更新/卸载/同步并执行 | **拆出 P1**；检测与执行分开；执行只对夹具 | 高危操作隔离 |
| 4. 登录注册找回全套 | 冒烟只留账密；其余进 P1，**接受人工验证码** | 合理性取舍 |
| 5. 设置各功能 | 收缩为**先做主题**；其余要清单 | 拒绝无边界范围 |
| 6. 下载安装应用 | 归入 P1-A，**不进 P0** | 耗时且高危 |
| 7. 会员权限 | 降为 **P2**，先做身份差异，不做价格文案 | 内容易变 |
| 8. 活动跳转展示 | 降为 **P2**，只测入口和跳转 | 内容易变 |

> [!question] 观察一下这个调整模式
> 8 条里，**2 条保留（1、2，但都加了约束）**，**2 条拆分降级（3、6 → P1）**，**2 条收缩（4、5）**，**2 条降为 P2（7、8）**。
> 没有任何一条是"完全砍掉"，也没有一条是"原样照做"。
> **这正是需求工程的实际形态：不是接受或拒绝，而是重新分层。**

## 自测

> [!question]- Q1：为什么"6 包全量升降级矩阵"被踢出日常，而不是完全砍掉？
> 因为它有真实价值——但它回答的是**"发版闸门能不能过"**，不是**"今天这版能不能用"**。
> 两个问题的时间尺度不同：日常回归要快（十几分钟），发布闸门可以慢（几小时）。
> **同一个测试内容，放在不同的调用时机，价值完全不同。**

> [!question]- Q2："纯图像识别不当主定位手段"，但 `about.py` 用了 OCR，矛盾吗？
> 不矛盾。区别在**层级**：
> - 主路径：UIA 定位 → 失败则 Win32 → 失败则标受阻
> - 兜底：某个**具体节点**（版本号）UIA 读不到时，局部截屏 OCR
>
> 图像识别用在"其他路都走不通的一个小点"，而不是"所有控件的默认方案"。
> **判据：它是万能替补（危险），还是特定问题的补偿（可接受）？**

> [!question]- Q3：方案为什么主动补了"WebView2 点不到时的受阻口径"？
> 因为如果不提前定义，**遇到时就会争论**：这是产品缺陷吗？是自动化没做到吗？要不要继续投入？
> 提前约定 = 把"未来的争论"变成"现在的决策"。
> **工程上，模糊地带是成本最高的地方。**

> [!question]- Q4：原需求第 1 条被改成了"注册表 + 文件版本"，为什么还要**补上**「基线安装 + 升最新」？
> 因为原需求关注的是"**怎么看版本**"（观测手段），而方案关注的是"**版本怎么来的**"（安装路径）。
> 只看版本 = 只验证了结果；加上安装路径 = 验证了**产出版本的过程**。
> 后者才是真正的 P0 闸门——**包装不上，版本对不对没意义。**

> [!question]- Q5：如果需求方坚持要把"设置各功能"写进范围，你会怎么回应？
> 参照方案的做法：**要求对方给出功能清单和验收标准**。
> 方案的原文是"其余要清单"——不是拒绝，是**要求把范围变可验收**。
> 先做的主题之所以能先做，是因为它有**明确判据**（亮度值 227~255 vs 41~53）。
> **无法写出判据的需求，先别写进自动化。**
