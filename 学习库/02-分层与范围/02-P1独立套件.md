# 02 · P1 独立套件

> P1 的组织原则：**每个套件单独跑，不串进 P0。** 理由和 P0 相反——P1 的每个模块都需要"特殊前提"（凭据、夹具、人工），前提不齐就跑不了，串进主链会让主链也跑不了。

## P1-A · 应用生命周期

**核心难点**：这里的应用**全是真实日常软件**。这是整份方案里风险最高的地方。

### 检测部分（安全）

三个列表要能刷新出数据：更新列表、可卸载列表、可同步列表。

> [!important] 「空」要区分两种
> - **接口失败** → 缺陷
> - **本来没有** → 正常
>
> 同步页未登录时只有登录提示、没有列表，属**正常状态**，不是缺陷。

### 执行部分（危险）

对**配置里的夹具应用**做下载安装、更新、卸载、同步。

**断言安装结果**：仍走系统卸载注册表 / 约定安装目录，**不靠截图**。

### 夹具的艰难选择

| 夹具角色 | 选定 | 关键理由 |
|---|---|---|
| 安装/卸载 | 网易云音乐 | 装完 55s 内注册表有条目；卸载器 `UnInstall.exe /S` 静默卸干净；**有安装器** |
| 更新 | **7-Zip 26.02** | 官方 26.02 静默装/卸干净；大厅更新列表认外部装的老版本 |
| 同步 | **永久留空** | 见下 |

> [!warning] 为什么"绿色单文件应用"当不了夹具
> 有一类应用是绿色单文件：装 = 下到下载目录**直接运行**，**从不写卸载注册表条目**，大厅卸载列表永不出现，详情页永远停在「一键安装」。
> 结果：「装上/卸掉」**根本无从断言**。而且它自己还要提权启动（非提权 `WinError 740`）。
> **审计要点**：按映像认安装器时**必须排除**这类，否则会误当向导去点，甚至被收尾 taskkill 打死。

> [!important] 为什么 sync 夹具永久留空
> 同步页列的是「**其他电脑已装的日常软件**」——实测 11 条：QQ、百度网盘、钉钉……
> **没有安全可点的执行对象**。点任何条目都是真装。
> 所以用例做成**只读断言**：登录后 `NoAppListBox` 出现、条目名可读、`InstallAllBtn` 存在但**绝不点**。
> **这是一个"承认做不到"的决策，比硬造一个伪造对象更负责。**

### 更新夹具的巧妙之处

「点更新」这件事的难点：大厅把新版本包下到 `C:\AsusMCenterDownload`，再拉起一个**英文 NSIS 向导**，不是静默的。

那目标版本号从哪来？——**运行时从向导标题读**（标题形如 `7-Zip 26.03 (x64) Setup`），**不写死**。

起点版本呢？——`tools/reset_fixture.py` 每轮**静默压回钉住的 26.02**。

```
每轮开始：reset_fixture.py 把 7-Zip 压回 26.02
   ↓
用例：从大厅点「更新」
   ↓
大厅下载 → 拉起 NSIS 向导 → 从标题读目标版本 26.03
   ↓
点 Install → 注册表 26.02 → 26.03 ✅
```

> [!tip] 这个设计为什么好
> 它同时解决了两个矛盾：
> ① **起点必须确定** → 用 reset 脚本钉死，不依赖上次跑完的状态
> ② **目标不能写死** → 从向导标题运行时读，产品换版本也不用改代码
>
> **"确定的起点 + 运行时读到的终点"**，这个模式可以迁移到任何"升级验证"场景。

### 名称口径的坑

| 场景 | 用什么名 |
|---|---|
| 大厅列表断言 | **大厅商品名**（`7-Zip（64位）`） |
| 安装结果断言 | **注册表 DisplayName**（`7-Zip 26.02 (x64)`） |

所以配置里 `name` 和 `registry_hint` 是**分开的两个字段**。混用会匹配不到。

## P1-B · 账号

| 场景 | 自动化程度 |
|---|---|
| 账号密码 | **全自动** |
| 短信登录 / 注册验证码 / 忘记密码 | 脚本点到「已发送」，**停下等你回填验证码** |
| 微软账号 | 测到系统/WebView 登录窗为止；**出 MFA 标人工**，不算脚本失败 |

**注册格式校验**：空、过短、非法字符、两次密码不一致 → 用 UI 或页面提示断言。**不依赖真注册成功**（真注册会污染账号池，单独一条「成功注册」用一次性号）。

> [!tip] 注册校验的聪明做法
> 反馈 = `RegisterBtn` 变灰 + 对应提示行变红。
> 但 **UIA 读不到颜色** → 按节点矩形截屏**数红像素**（阈值 50）。
> **规律：当语义信息读不到时，退到像素，但要选一个稳定的量化判据（红像素数），不要做模糊对比。**

## P1-C · 设置

- 先做 **浅色/暗色切换**：切换后主窗口外观变化，**重启进程后仍保持**。
- 其他设置项**等有清单再加**。

> [!warning] 方案原文一句很有力的话
> *「禁止写『设置各功能』这种无边界范围。」*
> "设置各功能"听起来完整，实际上是**没有验收标准**的表述。先做主题，因为主题有明确可测的判据（亮度值）。

内幕细节：三档是 RadioButton `LightMode`/`DarkMode`/`AuroMode`，**Toggle 模式不支持**；外观断言用主窗口**平均亮度**（浅 227~255 / 深 41~53，阈值 128）；**只按 AutomationId 找**（按名字会撞到同名 ToolTip）。

## 自测

> [!question]- Q1：为什么 P1 每个套件要单独跑，而不是合并成一个 P1 大全集？
> 因为 P1 各模块的**前提条件完全不同**：
> - P1-A 真装真卸 → 要提权
> - P1-B 密码登录 → 要凭据
> - P1-B 短信 → 要人工
> - P1-C 主题 → 要重启大厅
>
> 合并后，只要有一个前提不满足，整个 P1 都跑不了。分开则"有什么跑什么"。

> [!question]- Q2：三个列表里，"空"的两种含义是什么？为什么要区分？
> ① 接口失败（缺陷）② 本来没有（正常）。
> 不区分会导致**假缺陷**：同步页未登录本来就没列表，报成缺陷会污染数据、浪费时间。
> **判据来源**：用其他信号交叉验证——如未登录态就是"本来没有"的明确解释。

> [!question]- Q3：为什么 7-Zip 更新夹具要"每轮压回老版本"？
> 因为更新是**一次性资源消耗**：点完更新，版本就升上去了，更新列表里条目消失，**下一轮就没得测了**。
> reset 脚本是"重建测试前提"，和夹具复位的思路一致。
> **规律：任何"消耗型"测试资源都需要重置机制。**

> [!question]- Q4：目标版本"运行时从向导标题读"和"写死 26.03"相比，好在哪？
> 写死的问题：产品更新到 26.04 后，脚本还在找 26.03，**断言假失败**。
> 运行时读的好处：**脚本表达的是"应该升到向导宣称的版本"，而不是"应该升到某个具体数字"**。
> 这在被测对象版本频繁变化时特别重要——**断言要打在"逻辑关系"上，而不是"具体数值"上**。

> [!question]- Q5：为什么注册格式校验不真注册成功？
> 真注册会**污染账号池**——每跑一次多一个账号，很快无法管理。
> 所以策略是：**格式校验用假数据**（只看按钮是否禁用、提示是否变红），**真成功单独一条用一次性号**且由人决定跑不跑。
> **这是"高危操作隔离"的典型手法。**
