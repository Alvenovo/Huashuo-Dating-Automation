# 02 · 设计原则五条

方案原文列了 5 条原则。**别背，要看懂每条在防什么事故。**

## 原则 1：主流程要短、要稳

> *「安装、启动、首页、搜索、详情是一条；账号、装卸载、会员、活动各自独立，失败互不影响。」*

**在防什么**：把 8 个模块串成一条超长脚本——第 3 步失败，后面 5 步全不跑，你不知道到底坏了几处；而且跑一轮要一小时，没人愿意跑。

**怎么落地**：

```
安装层(P0-01/02) → 启动层(P0-03/04) → 冒烟UI(P0-05/06/07)
                                      ↘ 账号 P1-B（按需）
                                      ↘ 应用 P1-A（按需）
                                      ↘ 设置 P1-C（按需）
                                      ↘ 会员/活动 P2（按需）
```

右边这些**不在主链上**，谁有夹具有空谁跑。

## 原则 2：能读系统状态就不要点 UI

**在防什么**：把"验证结论"建立在 UI 渲染上，导致断言脆弱。

**具体选择**：

| 要验证 | 不用 | 用 |
|---|---|---|
| 版本 | 控制面板 | 注册表 `DisplayVersion` + exe `FileVersion` |
| 应用是否装上 | 详情页文案 | 系统卸载注册表条目 |
| 安装结果 | 截图 | 约定安装目录 + 注册表 |

→ 展开见 [[03-为什么能读状态就不点UI]]

## 原则 3：WebView2 按能力降级

> *「外壳控件用 UIA；页面点不到就标受阻，不假装全自动。」*

**在防什么**：为了"看起来是全自动"，改用图像识别点坐标撑场面——这种脚本维护成本极高，界面一改就废，而且失败原因不可解释。

**降级阶梯**：

```
① UIA 扫搜索框/列表项/按钮  → 扫到就用
② UIA 扫不到 → 查能否开远程调试端口 → 能则 Playwright 连进去点
③ 都不行 → 标「技术受阻」，P0 里只保留「窗口在、进程在」
```

> [!tip] 一个可以迁移的判断标准
> **「受阻」是一个可交付的结论**，不是失败。承认"这个页面自动化不了"比写一个靠运气过的脚本更专业。
> 方案在这点上很硬气：*「不要改成截图点选撑场面。」*

## 原则 4：数据依赖全部夹具化

> *「搜索词、可更新应用、可卸载应用、会员账号，都写进配置。线上运营一变，只改配置，不改脚本结构。」*

**在防什么**：把"QQ"、"7-Zip 26.02"这类会变的业务数据写死在脚本里。运营一调整，脚本全红，而没人知道是产品坏了还是脚本过期了。

**落地点**：`config.yaml` 里的 `search_keyword`、`fixture_apps.*`、`update_fixture.*`。

→ 展开见 [[02-配置与数据夹具化]]

## 原则 5：破坏性操作可逆且范围小

> *「专用机可以真装真卸，但只动夹具应用和大厅自己；不把随机软件当试验品。」*

**在防什么**：**这是最危险的一条**。大厅的更新/卸载列表里全是用户日常软件——点「全部更新」会把微信、WPS、Python3 全升一遍，点某个条目的「卸载」会真卸掉。

**护栏**：

1. 只对**配置里声明的夹具应用**执行装卸。
2. `UpdateAllBtn` / `InstallAllBtn` 列为红线，**绝不点**。
3. 破坏性用例加 `destructive` marker，需门禁。
4. 提权走一次性计划任务 `HallAutoP1`，用完即走。

---

## 五条原则之间的关系

```
原则1 主流程短稳
   ├── 依赖 → 原则2 读系统状态（少点 UI 才稳）
   ├── 依赖 → 原则3 能力降级（点不到就承认，别硬撑）
   └── 依赖 → 原则4 夹具化（数据可换，结构不动）
                         └── 支撑 → 原则5 破坏性可控（知道动谁才敢动）
```

一句话串起来：**为了稳（1），所以少点 UI 多读系统（2）；点不到的地方诚实降级（3）；会变的东西全抽到配置（4）；真要动机器时，范围锁死在夹具上（5）。**

## 自测

> [!question]- Q1：为什么"把 8 个模块串成一条超长脚本"被明确列为不做？
> 三个原因：① 失败归因困难——中间断了不知道坏几处；② 迭代慢——改一行要跑一小时；③ 大部分模块**根本不需要每轮跑**（会员、活动几天才变一次）。
> 短流程 = 快速反馈 = 有人愿意跑。

> [!question]- Q2：原则 3 说"标受阻"，这和"用例失败"有什么本质区别？
> 失败 = **产品有问题**，要提单。
> 受阻 = **我们的手段不够**，是已知限制，不应计入产品质量指标。
> 混淆这两者会导致缺陷数据污染，也会让团队对自动化失去信任。

> [!question]- Q3：原则 4 说"线上运营一变，只改配置，不改脚本结构"。如果改配置还不够呢？
> 那说明**抽象层级找错了**。比如把"7-Zip"整个写进配置没问题，但如果要做"任意应用都能装卸"的通用引擎，配置就撑不住了——这时该问的是"我们真的需要通用引擎吗"，而不是急着写。
> 方案的选择是：**只支持夹具，不追求通用**。

> [!question]- Q4：这五条里，哪一条如果违反了后果最严重？
> 原则 5。前四条违反的后果是"测试不可靠"，原则 5 违反的后果是"**测试把用户的机器搞坏了**"。
> 风险等级不同，所以原则 5 有最多硬性护栏（红线按钮、marker 门禁、提权隔离）。
