# 03 · 窗口与句柄的陷阱

> 前两条讲"怎么找到控件"，这条讲**"什么时候找控件会突然全都找不到"**。这类问题最耗时间，因为脚本会以毫无征兆的方式失败。

## 陷阱 1：首跑先出一个前置弹窗

**现象**：首装/升级后第一次启动，先出**独立顶层窗**「权限确认窗口」（同意/取消），**点完同意主窗口才出现**。

**后果**：`wait_main_window` 等主窗口会一直等到超时。

**解法**：等主窗口**之前**先处理前置窗 → `dismiss_pre_main_popups()`。

```
start_fresh()
   ↓
dismiss_pre_main_popups()   ← 先关前置窗
   ↓
wait_main_window()          ← 再等主窗
```

## 陷阱 2：大厅会恢复上次的页面

**现象**：冷启动时大厅**不会回首页**，而是恢复上次停留的页面（实测首跑落在了设置/关于页）。

**后果**：就绪判定（找导航、内容区、搜索入口）找不到 → 超时。

**解法**：判定结构缺失**且存在 `BackBtn`** 时，点返回回首页。

> [!tip] 这个解法的精细之处
> 关键在"**且存在 BackBtn**"这个附加条件。
> - 有 `BackBtn` → 说明在子页面 → 应该返回
> - 没有 `BackBtn` → 说明可能真有问题 → 不该盲目点
>
> 如果无条件点返回，可能会掩盖真正的产品缺陷。**加条件是为了区分"走错页面"和"产品坏了"。**

## 陷阱 3：登录后主窗口的 UIA Name 会变

**这是本项目最隐蔽的坑。**

| 状态 | Win32 标题 | UIA Name |
|---|---|---|
| 未登录 | 华硕大厅 | **华硕大厅** |
| 已登录 | 华硕大厅（不变） | **华硕应用商店** ← 变了 |

**后果**：pywinauto 的 `WindowSpecification` 按 `title_re` 匹配 **UIA Name**。登录态下解析**永远失败**（`ElementNotFoundError`），**重试无用**。

**解法**：用 `launch.concrete_main(pid, title_contains)` 按 **Win32 标题 + pid** 重包一个具体 wrapper。

> [!important] 为什么这个坑值得单独记
> 因为它的失败方式具有**极强误导性**：
> ① 报的是 `ElementNotFoundError` → 让人以为是"窗口没出现"或"超时不够"
> ② 实际上窗口好好地在那儿，只是**匹配的键变了**
> ③ 而且只在**登录态**出现 → 未登录时测得好好的，登录后突然全挂
>
> **规律：当"找不到元素"但元素明显存在时，先怀疑"匹配条件"，而不是"等待时间"。**

## 陷阱 4：登录窗和用户菜单会顶掉主窗口句柄

**现象**：登录弹窗是**独立窗**（`aid=LoginWindow`）；点已登录用户区打开的退出菜单也是**独立窗**。

**后果**：主窗口的句柄/wrapper 会失效或被遮挡。

**解法**：**一律按 pid 跨窗口找控件**（`_windows(pid)` / `_nodes(pid)`），不依赖"主窗口"这个对象。

```python
# 反例：绑定在主窗口上找
main.child_window(auto_id="MobileInputBox")   # 登录窗一开就找不到

# 正例：按 pid 全局找
_nodes(pid, control_type="Edit")              # 跨窗口有效
```

## 陷阱 5：句柄本身是会失效的

**现象**：主题用例切换浅色/暗色后**重启大厅**，窗口句柄和 pid 全换了。

**解法**：用例持有**可变引用**，重启后更新它，收尾还原才拿得到活的句柄。

> [!tip] 一个通用的认知
> **句柄（handle）是"当前时刻的引用"，不是"东西的永久地址"。**
> 窗口销毁重建、进程重启、控件被替换 → 句柄失效。
> 凡是跨"重启/关闭/重开"边界的操作，都要重新获取句柄。

## 陷阱 6：`handle` / `pid` 读取很慢

**实测**：就绪循环里 `main.handle` / `main.element_info.process_id` **各约 1s/次**。

**后果**：如果每轮循环都重新读，3 次循环就是 6 秒白等。这是"首页停留过长"的**二次根因**。

**解法**：这两个值在窗口生命周期内**是不变量** → **循环外取一次，缓存后传进去**。

```
❌ for i in range(3):
      h = main.handle          # 每轮 1s
      ...

✅ h = main.handle            # 只取一次
   for i in range(3):
      use(h)
```

> [!important] 规律
> **明确是"不变量"的东西，绝不要放在循环里重复获取。** 这在 UI 自动化里特别重要，因为每次 UIA/句柄查询都可能是一次跨进程调用。
> 排查"为什么这么慢"时，第一步就是找循环里的重复查询。

## 陷阱 7：`WindowSpecification` 是"懒解析"的

pywinauto 的 `WindowSpecification` 不是即时查找，而是**保存查询条件，每次用时重新解析**。

这带来两个后果：

1. **解析时机不可控** → 上面陷阱 3 的失败会在"第一次实际使用"时爆发，而不是创建时。
2. **重试无用** → 因为条件本身不匹配，重试多少次都一样。

**解法**：需要稳定引用时，用 `concrete_main()` 取**具体 wrapper**（`WindowSpecification.wrapper_object()` 的等价物，但明确用 Win32 标题重包）。

## 自测

> [!question]- Q1：为什么 `wait_main_window` 要先处理前置弹窗？
> 因为 `wait_main_window` 是**阻塞等待**主窗口出现。而首跑时主窗口**还没出现**（前置窗挡在前面）。
> 前置窗不处理，主窗口永远不会出现 → 等到超时。
> **顺序问题：前置动作必须在等待之前。**

> [!question]- Q2：登录后"找不到主窗口"，你会先查什么？
> 先查**匹配条件**，不是等更久。
> 具体做法：打印当前所有顶层窗口的 Win32 标题和 UIA Name，对比预期。
> 本项目就是靠这个发现"UIA Name 从华硕大厅变成华硕应用商店"。
> **诊断顺序：确认目标存在 → 再看匹配条件 → 最后才怪超时。**

> [!question]- Q3：为什么"按 pid 跨窗口找控件"比"绑在主窗口上"更稳？
> 因为登录/退出/菜单这些操作会创建独立窗口，主窗口的对象可能失效或被遮挡。
> 而 **pid 在整个进程生命周期内稳定**，且项目的做法是"趁窗口健康时先记下 pid"。
> **选择更稳定的锚点（pid > 窗口对象 > 控件对象）。**

> [!question]- Q4：`main.handle` 缓存这个优化，为什么能显著提速？
> 因为它把 N 次跨进程调用压成 1 次。实测每次约 1s，3 轮循环就是省下约 6s。
> 而且这类查询在 UIA 里是**同步的**——会真的阻塞脚本。
> **优化思路：先找"循环内的重复昂贵操作"，而不是先想"换个更快的框架"。**

> [!question]- Q5：如果让你给"句柄失效"设计一条通用防护，你会怎么做？
> 核心是**分清"什么变了、什么没变"**：
> - 进程重启 → pid 和所有句柄都变了 → 全部重取
> - 窗口重建 → 窗口句柄变了 → 重取窗口，控件可重找
> - 控件被替换 → 控件引用失效 → 重找控件
>
> 本项目的做法：把"会变的引用"放在用例级的可变容器里，在重启点显式更新。
> **不要用全局单例持有句柄** —— 那会在重启后静默变成悬空引用。
