# 01 · 三种定位手段与选择

## 全景对比

| 手段 | 能力 | 用在哪 | 致命限制 |
|---|---|---|---|
| **UIA**（pywinauto） | 读控件树、按 aid/name 定位、`invoke()` 点击 | 大厅外壳、WebView2 内页、登录窗 | 对 **NSIS 向导完全失效** |
| **Win32 消息** | `EnumWindows` 枚举、`WM_GETTEXT` 读文字、`BM_CLICK` 点击 | 厂商安装器/卸载器 | **UIPI 限制**：非提权点不动提权窗口 |
| **截图 + OCR** | 从像素里读文字 | 版本号（UIA 读到占位符时）、自绘按钮确认 | 脆弱、慢、依赖 OCR 引擎语言包 |

## 选择决策树

```
要定位一个控件
    │
    ├─ 它在大厅窗口里（外壳或 WebView2）？
    │       └─→ 用 UIA，按 AutomationId 找（不要按 name，会撞 ToolTip）
    │
    ├─ 它是厂商安装器/卸载器的对话框？
    │       └─→ UIA 一定是瞎的，直接走 Win32
    │              ├─ 有文字按钮 → 剥掉 (&X) 后按文字点
    │              └─ 自绘无文字 → 按面积认（或提权后 OCR 确认）
    │
    └─ 是大厅里的自绘/占位符节点？
            └─→ UI 读不到语义 → 退到截图 OCR，但只作兜底
```

## 为什么优先按 AutomationId 而不是按 name

本项目里有几处实测踩过的坑：

| 场景 | 按 name 的后果 |
|---|---|
| 设置页主题档位 | **撞到同名 ToolTip**，选中了错误的节点 |
| 同步列表条目 | name 是占位符 `AppStore.NetWork.AppListInfo`，真名在条目内 **Text 子节点** |
| 关于页版本 | name 是占位符 `ver` |
| 登录按钮 | 不勾协议时是灰的，`invoke()` **无效**（要处理状态） |

> [!important] 规律
> **AutomationId 是开发者给控件起的稳定标识；name 是给用户看的文本**（可能重复、可能被本地化、可能是占位符）。
> 优先 aid，name 只作辅助验证。

## 三个手段之间的"接力"设计

方案里的降级阶梯（对应原则 3）：

```
① 用 UIA 扫搜索框、列表项、按钮   → 扫到就用
② 扫不到 → 查进程能否开远程调试端口 → 能则 Playwright 连进去
③ 仍不行 → 该页标「技术受阻」
```

而**厂商向导不走这条阶梯**，是独立的 Win32 通道。这两条并行：

```
大厅 UI 路径：UIA ──(失败)──→ Playwright ──(失败)──→ 标受阻
厂商向导路径：Win32（因为 UIA 一开始就确定是瞎的）
```

> [!tip] 一个关键认知
> **"降级"不等于"一条路走不通再试下一条"。** 方案对厂商向导直接跳过 UIA 试错——因为探针已经实测确认"UIA 对它 0 descendants"。
> **提前探测、把确定的事实固化成结论**，比运行时反复试错高效得多。这就是 `工具/probe_*.py` 存在的意义。

## 探针工具的存在意义

| 工具 | 探什么 | 何时用 |
|---|---|---|
| `tools/probe_uia.py` | 大厅 UIA 树 | 换版本后复核控件图 |
| `tools/probe_win32.py` | 厂商对话框 + 控件文字 + 按钮矩形表 | 换安装器后复核 |
| `tools/probe_installer.py` | 截图 + OCR 兜底 + `PW_RENDERFULLCONTENT` | 需要看自绘内容时 |
| `tools/ocr_text.ps1` | 调 Windows 自带 OCR | 局部文字识别 |

> [!important] 探针是自动化的"侦察兵"
> 方案原文有一句很关键：*「专用机落地前，要在那台机器上用 Inspect / Accessibility Insights 看一次：搜索框是原生控件还是网页控件。结果会决定 P0-06 能不能按期自动化。」*
> **先探明，再写用例。** 不探明就写，等于赌。

## 自测

> [!question]- Q1：为什么 UIA 对大厅有效，对 NSIS 向导就失效？
> 因为 UIA 依赖程序**主动暴露无障碍信息**。WPF 和 WebView2 都内置了 UIA Provider，所以能读。
> 而 NSIS 是老式 Win32 程序，**不实现 UIA Provider**，只能通过经典 Win32 消息窗口机制访问。
> → 展开见 [[02-UIA为什么有时是瞎的]]

> [!question]- Q2：设置页主题档位"按名字找会撞到同名 ToolTip"，这提示了什么？
> 提示 **name 不是唯一标识**。UI 里同一个文本可能出现在多处（控件本身、它的提示、它的标签）。
> 而 AutomationId 是开发者显式指定的，**在同一窗口内唯一**。
> **做法：定位用 aid，验证用 name。**

> [!question]- Q3：为什么不给厂商向导也走"UIA → Playwright → 受阻"的阶梯？
> 因为那三步里，**前两步已经被实测证明无效**（NSIS 无 UIA Provider；也不是浏览器页）。
> 走一遍会浪费时间且让人误以为"再试试就能行"。
> **已确认的技术事实要固化成结论，不要每次运行时重新试错。**

> [!question]- Q4：如果 `VersionLabel` 的 UIA name 是占位符 `ver`，为什么不用 Win32 的 `WM_GETTEXT` 读它？
> 可以试——但 `VersionLabel` 在大厅的 WPF 窗口里，它的实际渲染由 WPF 负责，`WM_GETTEXT` 对 WPF 控件**未必能拿到内容**（WPF 是自绘的，不走标准窗口文本）。
> 方案的选择是截图 + OCR。这是**基于技术现实的判断**，不是随意选的。
> **启发：手段选择要看控件的"渲染归属"，不能只看它在哪个窗口。**

> [!question]- Q5：探针工具和用例的关系是什么？
> 探针是**一次性侦察**，产出**稳定知识**（写进 `项目知识库/探壳结论.md`）。
> 用例是**反复执行**，消费这些知识。
> 探针不是测试框架的一部分，它是**建立测试框架的前提**。
