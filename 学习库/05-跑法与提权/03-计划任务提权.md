# 03 · 用「定时任务」绕过权限墙

> **预计阅读 7 分钟** · 上一篇讲了"为什么绕不过去"，这篇讲**怎么绕**。

---

## 📖 阅读前 · 1 个名词先搞懂

### 名词：计划任务（Scheduled Task）

**大白话**：Windows 自带的功能，可以**预先设定"某个程序在某个时候以某个身份运行"**。

**类比**：**给保洁阿姨留的委托单**。
你不在公司时，她按单子进来打扫。**你不需要亲自在场，也不需要她的钥匙** —— 前台会放她进去。

**本题的用法**：预先留一张"**以管理员身份运行**"的委托单，之后**用普通身份去触发它**。

---

## 💡 核心思路（一句话）

> **不要"运行时提权"，要"事先准备好一个高权限通道"。**

```
❌ 走不通的路：
   脚本跑着跑着说"我要管理员权限"
        ↓
   系统弹出确认框
        ↓
   而这个框画在"安全桌面"上，脚本碰不到
        ↓
   卡死

✅ 走得通的路：
   事先（人工一次）：留一张"以管理员身份运行"的委托单
        ↓
   之后（每轮）：用普通身份触发这张单子
        ↓
   委托单让高权限身份去干活 → 畅通
```

---

## 🔑 关键：为什么"建"要钥匙，"触发"不要

这是整个方案的支点，值得单独想清楚。

| 动作 | 需要管理员权限吗 | 为什么 |
|---|---|---|
| **创建**一个高权限计划任务 | ✅ **需要** | 否则低权限程序就能给自己开后门 |
| **触发**一个已存在的高权限任务 | ❌ **不需要** | 系统假定：既然管理员建了它，说明**已经授权它被执行** |

> [!important] 这个"不对称"就是全部的秘密
> ```
> 创建 = 管理员做一次（人工）
> 触发 = 标准权限就能做（全自动）
> ```
>
> **所以：人工介入一次，换来之后永久自动。**

---

## 📝 具体怎么建（人工只做这一次）

在**管理员**身份的 PowerShell 里跑一行命令，创建一个叫 `HallAutoP1` 的任务：

```
创建任务，设定：
  · 以最高权限运行
  · 触发时执行「跑测试脚本」这个动作
```

之后**每轮都全自动**：

```
普通身份 → 触发这个任务 → 任务以管理员身份启动脚本
```

> [!tip] 为什么叫 "HallAutoP1"
> `Hall` = 华硕大厅（Hall）+ `Auto` = 自动化 + `P1` = 它主要跑 P1 那一层的用例（装卸应用那批）。
> 命名本身在告诉你"**这个任务是给哪一批用例提权用的**"。

---

## 🕳️ 三个实操的坑

### 坑 1：Git Bash 会把 `/Run` 当成路径

在 Git Bash（一种命令行环境）里，写 `/Run` 会被**自动转换成一个文件夹路径**，命令就失效了。

**解法**：在前面加一句"**别做路径转换**"的开关。

```
❌ 直接写 → 被转换 → 命令失效
✅ 加开关 → 正常
```

> [!tip] 这类坑的特征
> **在 PowerShell 里对，在 Git Bash 里错。**
> 遇到"**命令没变、换个命令行环境就失败**"时，先查**参数是不是被环境改写了**。

### 坑 2：权限不够时要"立刻失败"

方案里有个很好的设计：

> *「非提权直接跑脚本会在开头立刻失败并给出提示，不会白等 300 秒。」*

**好在哪**：
① **省时间** —— 300 秒白等
② **归因清晰** —— 立刻告诉你"这是权限问题"，而不是"超时（原因不明）"
③ **安全** —— 不碰任何东西就退出，不留下半完成状态

> [!important] 通用原则
> **前置条件检查放在最前面，并且要失败得又快又明确。**
> 不要等跑到一半才发现"哦，原来权限不够"。

### 坑 3：任务内容是写死的，临时要跑别的用例怎么办

计划任务的"动作"是**固定的字符串**（比如"跑 P1 那批用例"）。

如果临时想跑另一条用例（比如 P2 里某条需要提权的），方案的做法是：
```
① 临时改脚本里那一行，指向目标用例
② 触发任务
③ 跑完用 git checkout 还原
```

> [!warning] 这是权宜之计，不是好设计
> 问题：**忘记还原会导致后续行为异常**。
> 更好的做法是让脚本**接受参数**（跑哪条用例由参数决定）。
>
> ⚠️ **推断**：方案没做参数化，是因为**这个场景极少用**（就一两条用例），做参数化的收益不抵复杂度。
> **评价工程决策要看它解决的频率，不是看它"完不完美"。**

## 🎯 哪些操作需要提权，哪些不需要

| 操作 | 要提权？ | 原因 |
|---|---|---|
| 装/卸大厅 | ✅ 要 | 要写系统目录 + 改注册表 |
| 装/卸夹具应用 | ✅ 要 | 同上，**而且卸载器自己就是管理员进程** |
| 列表检测（只读） | ❌ 不要 | 只是读 |
| 读注册表 | ❌ 不要 | 读不需要权限 |
| **读**管理员窗口的文字 | ⚠️ 可以（不受限） | 但**不能点** |
| **点**管理员窗口的按钮 | ✅ 要 | 被 UIPI 挡住 |

> [!important] 最容易忽略的一条
> **「卸载器本身也是管理员进程」** —— 实测确认过。
>
> 所以：即使你是用普通权限启动的大厅，**点"卸载"之后弹出的那个卸载向导，是管理员的**。
> 你要操作这个向导 → **必须提权**。
>
> **认知：提权需求不只来自"我要写文件"，还来自"我要操作的对象本身是提权的"。**

> 提前给保洁阿姨留一张委托单（高权限任务）。
> **你不用亲自在场，前台会放她进去。**

> 创建高权限任务 = 要管理员（**人工一次**）
> 触发它 = 普通权限就行（**永久自动**）

### 口诀 ③：**先查票，再进场**

> 权限检查放最前面。
> **没票立刻出来**，别排到窗口才发现。

### 口诀 ④：**卸载器也是官**

> 大厅是普通身份启动的，
> **但它弹出来的卸载向导是管理员**。
> → 还是要提权。

## 🎤 应对提问

> [!question]- Q1：为什么"触发"一个高权限任务不需要管理员，而"创建"需要？
> 因为**创建和触发的权限要求不同**：
> - **创建**：需要管理员 —— 防止低权限程序给自己开后门
> - **触发**：只要对该任务有执行权限即可 —— 系统假定"管理员建它就是为了让它被执行"
>
> **这个不对称性是整个方案的基础。**

> [!question]- Q2：为什么不"每次需要时让人工输一次密码"？
> 那就退化成"**每条危险用例都要人工介入**"，失去自动化意义。
>
> 方案的判断：**人工一次（建任务）换永久自动** —— 对比"每次人工"成本差极大。
> **判据：人工成本是"一次"还是"每次"？一次可接受，每次不可接受。**

> [!question]- Q3：为什么要"立刻失败"而不是"等超时"？
> 三个好处：
> ① **省时间**（不用白等）
> ② **归因清晰**（直接告诉你"是权限问题"，而不是"超时"）
> ③ **安全**（不碰任何东西就退出，不留半完成状态）
>
> **通用原则：前置检查在最前，失败得又快又明确。**

> [!question]- Q4：这个方案的代价是什么？
> **留下一个长期存在的高权限入口。**
> 任何能以普通权限运行的进程，都能触发它并以管理员身份执行。
>
> 所以：
> - 专用测试机 → 可接受
> - 办公机/生产机 → **绝对不行**
>
> ⚠️ **推断**：这就是为什么方案反复强调"办公机不要 `--allow-install`" —— 不只是防止误装软件，也是**避免在高频使用的机器上留下这种通道**。

> [!question]- Q5：如果要求你改进"临时改脚本"那个权宜之计，你怎么做？
> 三个方向：
> ① **参数化**：让脚本接受"跑哪条用例"的参数
> ② **建第二个任务**：专门给那批用例用，动作固定
> ③ **用环境变量传参**（但计划任务设环境变量不方便）
>
> ⚠️ **但要先问：这个场景多久用一次？** 如果一年用两次，改脚本更划算。
> **不要为了"优雅"增加复杂度。**
