# 01 · 四层执行结构

> 前面讲"技术怎么实现"，这里讲"**实际怎么跑**"。

## 四层结构

```
① 单测层   tests/unit/         纯逻辑，毫秒级，办公机随时跑
              ↓ 改了代码/配置解析就重跑
② 安装层   tests/install/      P0-01/02，管理员，专用机
              ↓ 装好了才能测 UI
③ 冒烟层   tests/launch/test_p0_*.py   P0-03/04/06/07
              ↓ UI 能用才谈得上功能
④ 套件层   tests/launch/test_p1_*.py / test_p2_*.py
              账号 / 应用 / 设置 / 安全 / WB（各自独立）
```

## 什么时候跑哪一类

| 时机 | 跑什么 | 机器 | 失败怎么办 |
|---|---|---|---|
| 改了 Python / 配置解析 | `tests/unit` | **办公机** | 先修计算，**不要去装软件** |
| 新安装包、要验版本 | `tests/install`（P0-01/02） | 专用机 · 管理员 | 后面窗口测试**全部停** |
| 安装已通过，问这版能不能用 | P0-03～07 冒烟 | 专用机 | 安装结果仍算数；启动失败则不做搜索 |
| 有测试号 / 夹具应用 | 对应 P1，**一次只跑一类** | 专用机 | 验证码没回填记阻塞，不记产品缺陷 |
| 发版前 | P0 全套 + 已具备夹具的 P1；P2 可选 | 专用机 | P0 红则不发；活动下线可跳过 |

> [!important] "改了代码先跑单测，不要去装软件"
> 这条看似简单，但很容易违反：改了版本解析逻辑，直接跑安装用例验证——**装一次十几分钟，还占着专用机**。
> 而单测 101 条只需 **24 秒**，就能覆盖版本解析的绝大部分情况。
> **原则：能在低成本层验证的，不要上高成本层。**

## 各套件的具体命令

| 套件 | 命令要点 |
|---|---|
| 单测 | `-m unit`，无参数 |
| 安装 | 管理员 PowerShell 跑 `run_install_elevated.ps1`，日志 `reports/install_run.log`（头行写 `admin=True/False`） |
| 冒烟 | `.\run_p0_launch.ps1` |
| P1-A 检测 | `-m "apps and not destructive"`，**非提权可跑** |
| P1-A 真装真卸 | `schtasks /Run /TN HallAutoP1`，**0 人工** |
| P1-A 同步 | 需 `HALL_TEST_USER/PASSWORD`，约 25s，占屏，跑完自动登出 |
| P1-B 登录 | `-m login` + 环境变量 |
| P1-B 微软 | 只需 `HALL_MS_USER`，本机有缓存会话时无人值守 |
| P1-B 人在环 | `-m manual -s`，**只在用户自己终端** |
| P1-C 主题 | `-m settings`，约 2 分钟，**屏幕会忽明忽暗并重启一次大厅** |
| P2 安全 | `-m security`，缓存命中约 20s |
| P2 WB | `-m wb`，约 1 分钟，**绝不点「一键安装」** |

> [!warning] 三条最容易忘的约定
> ① 本机 `python` **不在 PATH** → 一律 `.venv\Scripts\python.exe`，带 `-X utf8`
> ② 跑批命令必须带 **`.\`** 前缀（PowerShell 相对路径）
> ③ Git Bash 里 `schtasks /Run` 会被**路径转换**吃掉 → 必须 `MSYS_NO_PATHCONV=1`

## 一个有意思的约束：为什么"一次只跑一类"

方案里写：**有测试号 / 夹具应用 → 对应 P1，一次只跑一类。**

理由：
- **占屏**：UI 套件会真的操作桌面，同时跑会互相干扰
- **状态污染**：应用套件会装卸软件、账号套件会改登录态、主题套件会重启大厅
- **归因清晰**：一次一类，失败时不用猜是哪一类引起的

> [!important] UI 自动化的特殊约束
> 非 UI 测试可以并行跑（互不干扰），**UI 测试天然是串行的** —— 因为桌面只有一个，鼠标键盘只有一套。
> 这直接导致"总耗时 = 各类耗时之和"，所以**每类的耗时控制很重要**（这就是为什么 P0 要"十几分钟"、P2 要"抽检"）。

## 提权相关

安装层和 P1-A 真装真卸都需要**管理员权限**。提权机制的细节见 [[03-计划任务提权]]。

**关键设计**：提权不是"让脚本自己提权"，而是**预先建好一个高权限计划任务，运行时用标准权限触发它**。

## 自测

> [!question]- Q1：为什么改了版本解析逻辑，应该先跑单测而不是安装用例？
> 成本差三个数量级：
> - 单测：**24 秒**，办公机，无副作用
> - 安装：**约 77 秒到几分钟**，专用机，需管理员，会真的改机器状态
>
> 而且单测能覆盖版本解析的**边界情况**（各种畸形文件名、大小写 S、段数不齐），安装用例只能覆盖"这一个包"。
> **用最低成本层做最大覆盖。**

> [!question]- Q2：为什么 UI 套件必须串行，而单测可以并行？
> 因为 UI 套件共享**唯一的物理资源：桌面**。
> 两个套件同时操作鼠标键盘，会互相抢焦点、抢窗口、抢剪贴板。
> 而且状态会互相污染（一个在登录、一个在登出）。
> **认识：UI 自动化的并行度受限于"物理资源数"，通常是 1。**

> [!question]- Q3："P0 红则不发"和"活动下线可跳过"，这两条规则的区别在哪？
> **判据的确定性**：
> - P0 红 → 明确的失败信号 → 阻断发布
> - 活动下线 → 可能是正常运营行为，不一定是缺陷 → 跳过
>
> 区别的本质是"**这个失败是否一定是产品问题**"。确定的失败才阻断，不确定的失败只记录。

> [!question]- Q4：为什么安装用例的日志要记录 `admin=True/False`？
> 因为安装必须在管理员权限下跑。如果日志里 `admin=False`，那失败原因就明确了——**是权限问题，不是产品问题**。
> 而且非提权跑会**在权限检查处就失败，不会碰已装大厅**（安全的失败）。
> **好的日志设计：把"环境前提"和"执行结果"分开记录，便于快速归因。**

> [!question]- Q5：如果要在另一台机器上部署这套自动化，你会按什么顺序验证？
> 参照方案的"落地顺序"：
> ① 专用机装包路径配好（配置项，脚本只读配置）
> ② 提权跑通 P0-01/02（装、对版本、升级）
> ③ **探壳**：UIA 能否点到搜索 → 决定 P0-03~07 能不能做
> ④ 有测试号后做密码登录
> ⑤ 有夹具应用后做 P1-A
> ⑥ 短信/微软/注册/主题/会员/活动按夹具齐套再加
>
> **顺序原则：先验证"地基能力"（能不能装、能不能读），再验证"业务能力"。**
