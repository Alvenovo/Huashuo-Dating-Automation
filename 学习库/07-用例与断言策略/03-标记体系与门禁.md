# 03 · 标记体系与门禁

> 这套机制解决"**同一份代码，在不同机器/不同权限/不同完备度下，怎么跑得都对**"。

## marker 全景（`pytest.ini`）

```ini
markers =
    unit: 不改机器状态
    install: P0 安装 / 升级
    launch: P0 启动 / 首页就绪
    smoke: 冒烟
    destructive: 会装卸华硕大厅或夹具应用，需 --allow-install 或 HALL_ALLOW_INSTALL=1
    login: P1 账号相关；密码登录用例需 HALL_TEST_USER / HALL_TEST_PASSWORD
    apps: P1-A 应用生命周期；检测类不改状态，真装真卸类同时带 destructive 走门禁
    settings: P1-C 设置页；会改客户端外观档位，用例收尾还原
    security: P2 安全验证；只读安装包与产品目录，只写工作目录
    wb: P2 WorkBuddy 入口；单机未登录态只读+点击，绝不点「一键安装」
    manual: 人在环用例，只在用户自己终端显式跑，无人值守套件一律排除
```

**注意每个 marker 的描述里都写了"副作用"**（改不改状态、需不需要凭据）。这是**给选择跑什么的人看的**。

## 两种分类维度

这些 marker 其实混了两种维度：

| 维度 | marker | 作用 |
|---|---|---|
| **功能分组** | `install` `launch` `apps` `login` `settings` `security` `wb` | 选择跑哪一类 |
| **副作用/前提** | `unit` `destructive` `manual` | 约束执行条件 |

**为什么要混在一起**：因为实际使用时要**组合**：

```bash
-m "apps and not destructive"   # 功能=应用生命周期的检测部分
-m login                        # 功能=账号
-m manual                       # 前提=人在环
```

## 门禁机制

```python
def _allow_install(config) -> bool:
    return config.getoption("--allow-install") or os.environ.get("HALL_ALLOW_INSTALL") == "1"

def pytest_collection_modifyitems(config, items):
    """收集阶段：给 destructive 用例加 skip 条件。"""
```

**双重开关**：命令行 `--allow-install` 或环境变量 `HALL_ALLOW_INSTALL=1`。

> [!tip] 为什么要有环境变量开关
> 因为计划任务（`HallAutoP1`）跑的是 PowerShell 脚本，**不方便传命令行参数**。
> 环境变量可以在脚本里设置，然后 pytest 读取。
> ```
> run_p1_apps.ps1 里：
>   $env:HALL_ALLOW_INSTALL = "1"
>   pytest -m apps
> ```
> **设计考虑：门禁开关要能从两种入口触发（命令行 + 环境变量）。**

## 为什么门禁放在"收集阶段"

```python
def pytest_collection_modifyitems(config, items):
    # 在收集完用例、开始执行之前，给不该跑的用例加 skip marker
```

**好处**：用例**根本不会被启动**，而不是启动后自己判断并退出。

对比：

| 做法 | 后果 |
|---|---|
| 用例内 `if not allow_install: pytest.skip()` | 每个用例都要写；容易漏；且 import 和执行开销已产生 |
| **收集阶段统一加 skip** | 一处集中；不可漏；开销为零 |

> [!important] 集中式门禁的通用模式
> **把"能不能跑"的判断从用例层上移到框架层。**
> 好处：① 不会漏 ② 用例代码只关心业务逻辑 ③ 策略改一处全生效

## 破坏性用例的双重防护

方案里对最危险的操作（`UpdateAllBtn` / `InstallAllBtn`）用了**两层**：

```
第 1 层：marker 门禁（destructive）
   → 防止"误跑"

第 2 层：代码红线（绝不点某些按钮）
   → 防止"脚本逻辑写错"
```

> [!warning] 为什么需要两层
> 它们防的是**不同的失效模式**：
> - 门禁防的是**人的失误**（忘了加参数就跑了）
> - 红线防的是**代码的失误**（万一门禁被绕过、或者逻辑写错点到全部更新）
>
> 而且在办公机上，**门禁可能是"该加但没加"**，此时只有红线能救。
> 方案原文：*「办公机不要 `--allow-install`」* —— 本质是**默认关闭危险能力**。

## 用例组织的一些约定

从代码里能看出的约定：

| 约定 | 例子 |
|---|---|
| 用例名带编号 | `test_p0_01_install_baseline` |
| docstring 首行写中文业务描述 | `"""P0-01 干净安装基线包：装完注册表版本与「关于」页版本一致"""` |
| 相关 marker 叠用 | `@pytest.mark.apps` + `@pytest.mark.destructive` |
| 需要凭据的用例显式声明 | `@pytest.mark.login` |

> [!tip] docstring 首行的双重作用
> ① **给人看**：用例名是英文的，业务人员看不懂
> ② **给报告用**：`conftest._case_title(item)` 取 docstring 首行作为中文说明
>
> **一份信息两处受益** —— 这是好设计的特征。

## `manual` marker 的特殊约束

```ini
manual: 人在环用例，中途停下等人工输入（会真发短信）；
        只在用户自己终端显式 -m manual 跑，无人值守套件一律排除
```

**实现**：非交互式终端（stdin 不是 tty）**自动 skip**。

> [!important] 为什么这个自动判断很关键
> 因为代理侧（自动化执行环境）跑这些用例会**永远卡在 `input()`** 上，直到超时。
> 更糟的是**会真发短信、真改密码** —— 副作用不可逆。
>
> **设计：让危险用例在没有人的环境里自动不跑，而不是靠"记得不要跑"。**

## 自测

> [!question]- Q1：为什么 marker 的描述里要写清"副作用"？
> 因为**选择跑什么的人需要知道代价**。
> 比如 `-m settings` 的描述里写"会改客户端外观档位，用例收尾还原" —— 这告诉执行者：
> ① 屏幕会变化 ② 不用担心（会自动还原）
>
> 如果只写 `settings: 设置页`，执行者不知道会不会留后遗症，就不敢跑了。
> **好的元数据要回答"这会发生什么"。**

> [!question]- Q2：`destructive` 门禁为什么要有环境变量这个入口？
> 因为计划任务触发时**不方便传命令行参数**（任务的"操作"字段是固定的字符串）。
> 环境变量可以在脚本内部设置，更灵活。
> **推广：任何"开关"设计，考虑它的所有触发方式（CLI / 环境变量 / 配置文件）。**

> [!question]- Q3：门禁放在收集阶段，和放在用例内，差在哪？
> **收集阶段**（本项目）：用例被标记为 skip，**根本不会执行**，也不会有 fixture 建立开销。
> **用例内**：用例已经开始执行，fixture 可能已经建立（比如已经启动了客户端！）才发现不该跑。
>
> 对破坏性操作，这个差别很关键：**在执行任何副作用之前就应该拦截。**

> [!question]- Q4：为什么标记体系要同时包含"功能维度"和"前提维度"？
> 因为实际使用是**组合查询**：
> ```
> 我要跑"应用生命周期里不改机器状态的部分"
>   → -m "apps and not destructive"
>
> 我要跑"除了人在环之外的所有"
>   → -m "not manual"
> ```
> 只按功能分 → 无法表达"只跑安全的"；只按前提分 → 无法表达"只跑应用的"。
> **两个维度正交，才能灵活筛选。**

> [!question]- Q5：如果让你再加一个 marker，你会加什么？
> 参考当前空缺：
> - `slow`：标记耗时长的用例（如主题套件会重启大厅），日常回归可排除
> - `flaky`：标记已知偶发的用例，报告里区别对待（但要谨慎，容易变成"容忍失败"的借口）
> - `nondestructive`：显式标记只读用例，可以放心在办公机跑
>
> 判断标准：**新 marker 是否对应一个真实的筛选需求？** 有需求才加，不要为了分类而分类。
